③ 三层根因

R1 · batch 双通道回流（直接原因）

batch 子任务用 handoff 回发起者时，正文走两条路：handoff 自建一条 dispatch，maybeCompleteBatch 又把同一结果放入 aggregate。reviewer 因而对同一材料收到直接回流和系统汇总两次触发。

R2 · 结果可见性没有分层（根因）

finish 不是“完成整个 run”，而是当前 dispatch 未继续路由时的默认动作；当前实现无论 dispatch 是 fanout 内部子任务还是汇总节点，都会发布 collaboration_result。系统缺少“内部结果”和“面向用户最终结果”的权限边界。

R3 · 执行中上下文陈旧 + 错误话术（放大器）

reviewer 开始处理 #1 后，上下文已固定，随后到达的 aggregate 不会动态进入该模型回合；这不是简单扩大 transcript 就能解决的问题。与此同时，乒乓提醒硬编码“辩论轮次”，在非辩论任务中推动了不必要的二次提交。

④ 修复方案（按性价比排序）

  1. 必修fanout 输出内部化：并行子任务默认只写入 attempt output，不直接发布用户可见的 collaboration_result。
  2. 必修batch 回发发起者去重：fanout 的 handoff 目标等于 batch initiator 时，将 handoff message 作为内部结果保存，不再创建额外 dispatch；aggregate 从 attempt output 汇总。
  3. 必修终态双重防线：dispatch 开始前及发布结果前重新检查 run；completed/failed/cancelled 后的迟到结果标记 cancelled，不再公开发布。
  4. 建议乒乓提醒文案中性化：改为提醒检查信息是否充分，不再假设任务属于辩论。
  5. 长期引入 response group：按根 dispatch/汇总分支实施 at-most-once 最终回复，避免用“任意 finish 清空整个 run”误伤正常并行和多收件人场景。

⑤ 复核说明

当前实现的队列领取已限定 run 必须为 running，并限制同一 Agent 同时只有一个 running attempt；finalizeRun 也会在仍有 queued/running dispatch 时拒绝完成 run。因此原报告“02:42:31 run 已 completed，之后仍领取 #2/#5”的表述与实现及顶部 02:38–02:44 的持续时间不一致。更可信的解释是：02:42:31 发布了第一条默认 finish 结果，但 run 直到 02:44:03 清空开放 dispatch 后才 completed。
