# 狼人杀入口与消息显示异常复盘

日期：2026-10-18，2026-10-19追加消息展示修复与验收。对应用户反馈的两场游戏与回复显示差异。此前切换范围见[业务灰度记录](autonomous-collaboration-service-cutover-2026-10-18.md)。

## 结论

两场游戏实际走的是旧动态接力，而非 AC6 已验收的受控规则流程。旧入口可由模型自行设定规则和角色；Runtime 接受本轮责任完成，不代表平台已验证游戏终局。只开放一个验收房间后，其他房间的页面仍默认回落到旧入口，没有明确提示能力差异，这是本次主要产品缺口。

消息显示差异则来自两个不同问题：过程正文和工具提交摘要的语义未区分，以及 SDK 完成块被当作另一段正文重复累计。页面没有把已有完整游戏记录丢掉；第一场的其他角色实际上没有获得执行任务。

## 第一场：结束了执行，没有完整游戏证据

Run `5d2bec69-dfd9-4751-84e3-3d8c7b7dad46`，房间 `5a6c7835-db56-4e31-b562-4db3ed206d3a`，22:47:26–22:53:48。

- 请求为旧 `entryVersion=1`，协议是 `dynamic_collaboration`；没有 autonomousCollaboration 契约，也没有任何 `autonomous_flows` 记录。
- 实际4次 SDK 调用，仅涉及主持鸡腿、nim、小牛吗三个角色。其他三名玩家没有 Dispatch，不存在等待显示的完整会话。
- 主持在过程正文中提出“2狼、1预言家、2平民”，只向两名狼人发牌并收集首夜行动；最终摘要又改称“2狼3好、无神职”。模型自行判断首夜后2狼2好满足狼胜，随后提交 complete。
- 该终态证明旧协作责任被接受结束，不能据此证明所有玩家已执行、神职规则一致，或完成了平台支持的狼人杀流程。历史 completed 事实和文本均保留，未把它改造成已验证游戏。

因此，用户看到的“只有三个角色输出”反映实际执行缺失，而非聊天列表过滤掉三个人的回复。

## 第二场：私密上下文阻止继续发牌

Run `b7370b8c-591d-4b14-b243-c5e3ab48d85f`，同一房间，23:14:27–23:21:08。

- 同样走旧 entryVersion1 / dynamic_collaboration，没有受控游戏流程。
- 鸡腿先向找茬员私密发放狼人牌并得到回复。主持的后续上下文包含这份狼人秘密，之后再尝试向其他角色发送身份任务，被 `PRIVATE_ROUTE_REQUIRES_SCOPE` 阻断。
- “再次声明 private”不能让新收件人取得已有私密来源的权限；本次权限拒绝正确。后续 Completion Engine 的任务阻断/租约提示属于失败汇总，首要原因是私密来源越界。
- 没有放宽 ACL、重新运行原根、清除 unknown，或伪造其他玩家行动。新游戏应通过独立玩家 Scope 和规则披露推进。

## 生成中的内容为何与最终消息不同

旧 SDK 回合的可见过程正文经 llm.snapshot 临时显示；正式交接使用 consult.objective，最终结果则使用 Agent 自己提交的 complete.summary。第一场最终房间消息与工具提交摘要一致，页面没有自行把长文改写成摘要。两者本来就可能不同，但原标签“正在回复”让过程正文看起来像最终消息。

另有独立解析错误：Claude SDK 将每个完成块分别发成单块 assistant 消息。例如原始流的 thinking=0、text=1，完成文本却位于独立 assistant.content[0]。旧解析器按局部0再存一次，造成同文重复。第一场开局正文实际为661字符，原 LLM 输出为1324字符，即两份正文加分隔换行。

使用真实安装 SDK 连接本地 Messages SSE，复现得到 `msg_local_fixture:1` 增量和 `msg_local_fixture:0` 完成快照，修复前返回同文两次。无需真实供应商请求即可确认原因。

## 修复范围

1. 服务处于 execute 房间灰度时，未开放的旧房间和新建房间不再默认展示旧接力输入。页面明确显示尚未开放，提供已开放房间的跳转；旧模式保留在主动选择的“高级 · 手动编排”中，并说明不提供规则游戏自动裁决与完整回放。
2. 生成区显示“正在生成 · 过程草稿”，说明最终消息来自实际提交或规则公告；旧完成消息显示“成员提交结果”。角色名称优先取 span 的 agent.id。已结束 span 或终态 Run 的迟到增量/快照不会重新出现在最终消息之后。
3. SDK 文本解析按同一消息内原始文本块位置匹配完成块，不按字符串相同来去重。相同文字出现在两个不同块时仍保留两次；thinking 仅发活动信号，不进入可见文本。保留最终 result 覆盖语义与原生工具权限检查。

没有修改历史游戏事实、共享私密原文、替模型补行动、扩大房间 allowlist，或降低既有超时与预算。后端已正常重启加载解析修复，前端按现有开发服务加载更新。

## 2026-10-19 消息展示修复

用户继续反馈：气泡短暂展示“思考内容”，最终换成一段简短结论，且正文近似纯文本。前一次增加“过程草稿”标签仍不足以解决这个交互问题。

这里短暂出现的是模型可见的普通过程正文，并非 SDK 的隐藏 thinking 块。带控制工具的回合会通过 `agent.complete.summary`、交接目标或流程公告正式交付；模型普通正文与正式工具字段可能不同。原工具描述又把 summary 称作摘要，容易诱导模型压缩实际结果。普通工具轮的过程正文还可能持久化为 informational 消息。Markdown 已有渲染器，但软换行会合并；规则流程的权威终局正文则使用角色 ID、无 Markdown 标题及 JSON 行动记录，直接渲染仍难阅读。

本次完成的调整：

1. API 增量、API 收尾与 SDK 快照统一标记回合展示意图。带控制工具的过程正文只在聊天区显示成员执行状态；不进入回复气泡，也不再写成中间 informational 消息。诊断 Trace 和恢复 checkpoint 保留原响应。普通无控制工具回复继续流式显示，审查协议继续隐藏，终态后的迟到流继续拒绝。
2. 明确 `agent.complete.summary` 是接收方看到的完整交付正文，要求按任务需要提供结果、依据与局限，可用 Markdown 标题、列表、表格或代码块。字段名、解析约束、权限及预算保持原契约；不会自动把过程原文拼入最终回复。
3. 通用正文保留软换行，改善段落、标题、列表间距。代码缩进与消息原文复制保持原字节。
4. 已完成的 `werewolf-five-v1` 终局增加只读阅读视图：胜方、全部身份、分阶段事件和可展开的接受行动；将角色 ID 映射为角色名，自称与真实身份分开标注。原始消息可展开、可原样复制。仅对带正式发布元数据及已完成流程状态的已知终局格式启用；其他消息回退原 Markdown。没有改写 `flowFinal`、冻结规则、消息正文或历史游戏事实。

模型是否提供足够细节仍取决于正式提交内容及原有输出预算；客户端不会编造缺失的说明。旧 informational 历史消息没有迁移，未执行的后续回合会采用新版运行时表达指导。
