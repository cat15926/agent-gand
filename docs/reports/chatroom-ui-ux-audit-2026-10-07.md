# 聊天室 UI 与交互体验检查

实施结果见：[聊天室 UI 优化实施与验收](chatroom-ui-optimization-2026-10-07.md)。
日期：2026-10-07。范围：本地业务页面 `http://localhost:5173/` 的新建房间、已有多任务房间、失败任务、引用回复、执行轨迹及响应式布局。本次为检查与分析，未修改应用代码、发送任务、调用模型或归档房间。

## 结论

当前聊天室同时承载消息阅读、任务配置和底层运行诊断，三个层次都常驻主界面，导致阅读空间不足、配置负担偏重、任务上下文难以辨认。应先修复查看轨迹导致其他任务消息消失的问题，再缩减常驻配置和执行信息，最后统一视觉与交互细节。

检查使用真实页面和现有房间，覆盖 1440、1280、1279、1024、768 和 390px 屏宽；手机检查高度为 844px，其他为 960px。浏览器 JavaScript 异常为 0，页面没有整体横向溢出；但这两个指标不能证明内容已经易读、操作入口完整。

## 实测证据

| 场景 | 实际表现 | 影响 |
| --- | --- | --- |
| 多任务房间查看第 1 轮轨迹 | 普通消息从 8 条变为 2 条，任务卡仍有 3 个 | 用户会误以为其他任务的聊天记录丢失 |
| 1440 × 960，已完成房间 | 消息滚动区高 346px，底部任务配置高约 380px，顶部标题和执行信息高约 186px | 房间内容区域中，消息阅读只占约 38% |
| 390 × 844，侧栏收起 | 消息区高 117px，聊天列宽 286px | 只能看到少量消息，阅读被配置区域压缩 |
| 390 × 844，展开房间列表 | 消息区高 52px，聊天列宽 174px，输入框宽 118px | 页面虽不横向溢出，实际已经难以阅读和输入 |
| 1280 → 1279px | 右面板突然消失，聊天列宽从 648px 变为 967px | 1px 的窗口变化引起 319px 的布局变化，并丢失功能入口 |
| 普通消息点击“回复” | 输入区仍显示“新任务”和“发送新任务”，只增加引用条 | 回复、继续执行和另起任务的区别需要用户自己推断 |
| 手机回复按钮 | 默认透明度为 0，尺寸约 22 × 16.5px | 悬停交互不能提供可靠的触屏入口 |
| 房间标题旁的 `•••` | 直接弹出归档确认，而非打开菜单；本次取消了确认 | 图标暗示“更多”，实际动作与预期不一致 |
| 历史房间刷新 | 选中“调研项目团队”后刷新，回到最新的“你好”房间 | 阅读位置和工作上下文不能保持 |

这些尺寸对应检查时的两个成员、三个任务房间；成员、执行记录、说明文案和展开状态增加时，占用还会变化。未启动新的运行来测量流式输出、真实待审批或软件键盘场景。

## 优化项与优先级

P0 指影响聊天记录完整呈现的问题；P1 指影响主要操作和阅读的问题；P2 指效率、可读性及一致性提升。

| 编号 | 优先级 | 问题 | 建议 |
| --- | --- | --- | --- |
| U01 | P0 | 查看任务轨迹覆盖整个房间的消息状态 | 将房间消息与所选任务详情分别存储，查看任务只改变检查面板的上下文 |
| U02 | P1 | 完整任务配置持续占据输入区，手机阅读空间尤其少 | 默认保留接收人、输入框、发送按钮；策略、工作流、约束、默认偏好进入“执行设置” |
| U03 | P1 | 手机两条左侧导航固定占用宽度，展开列表继续挤压聊天 | 房间列表改为覆盖式抽屉；手机主导航收进菜单或底部导航 |
| U04 | P1 | 小于 1280px 时运行检查面板被隐藏，没有替代入口 | 保留“任务详情／执行记录”入口，窄屏通过抽屉或全屏面板打开 |
| U05 | P1 | 成员、接收人、策略、工作流、房间默认偏好同时要求理解 | 明确“房间成员”和“接收人”，提供任务场景预设，保留现有高级设置和编排语义 |
| U06 | P1 | 失败提示偏向底层错误，缺少直接的恢复路径 | 在失败任务卡显示原因摘要、已保留结果、可行的下一步；支持带目标和成员重新编辑 |
| U07 | P1 | 刷新、返回和重新进入不能保持选中房间与阅读位置 | 将房间和任务选择写入 URL 或持久状态，保存每个房间的阅读锚点 |
| U08 | P1 | 所选任务与房间历史调度记录混合显示，选择状态不明显 | 检查面板明确显示“第 N 轮”，所有记录按同一任务过滤，房间历史作为独立视图 |
| U09 | P1 | 手机“回复”依赖悬停，更多菜单和重命名入口不符合预期 | 触屏常显操作或消息菜单；房间菜单提供显式重命名、设置及归档 |
| U10 | P2 | 任务目标、用户消息、执行状态和诊断信息重复呈现 | 已完成任务卡默认压缩，突出最终答复和成果，协作活动及技术证据按需展开 |
| U11 | P2 | 元信息常用 10–11px 暗灰文字，层级和对比度不足 | 统一字号与灰阶，确保关键状态和辅助说明在深色背景下易读 |
| U12 | P2 | 翻阅历史时缺少新消息提醒和回到底部入口 | 增加“有 N 条新消息”和“回到最新”，保持现有尊重手动滚动的行为 |
| U13 | P2 | 长文、代码和成果仍主要依赖整条消息操作 | 增加代码块复制、长文展开、成果入口和消息内搜索；长会话再评估分批加载 |
| U14 | P2 | 加载态、发送快捷键、禁用原因和界面术语反馈不统一 | 首屏使用加载态；明确发送方式与按钮禁用原因；统一产品术语和键盘焦点反馈 |

### U01：查看轨迹不应改变消息历史

复现步骤：打开有三个任务的“你好”房间，确认显示 8 条普通消息，再点击第 1 轮“选择此任务查看轨迹”。页面随后只保留该任务的 2 条普通消息，其他轮的任务卡仍保留。数据库记录并未在这次操作中删除，问题发生在前端展示状态。

[TaskCard](../../apps/web/src/components/TaskCard.tsx) 调用 `setActiveRun`，随后 [store](../../apps/web/src/store.tsx) 的 `runDetail` 分支以单个 Run 的消息覆盖 `state.messages`；[RunView](../../apps/web/src/components/views/RunView.tsx) 又使用这个列表渲染整个房间的所有任务，因此其他任务的消息暂时消失。单任务详情里的引用查找也会失去其他任务的消息上下文。

预期交互：点击“查看执行记录”后，聊天位置和全部房间消息保持，任务卡显示选中状态，右侧检查面板或抽屉切换到该任务。

### U02–U04：保证阅读区域和功能入口

输入区复用了完整 [TaskComposer](../../apps/web/src/components/TaskComposer.tsx)，默认就有对象按钮、三行输入、两个策略选择、约束入口、工作区说明和预览按钮。顶部又逐条展示当前任务的外部执行记录。即使记录全部完成，仍占据固定头部空间。

建议默认输入区采用两到数行自动增长的输入框，保留接收人、紧凑设置摘要及发送；配置表单使用弹层或抽屉，预览计划也采用可收起区域。头部默认只展示房间名称、成员、当前状态和“执行详情 N 项”，完成的执行记录收进详情。

桌面房间列表和检查面板均应支持收起，检查面板按需打开。手机用覆盖式抽屉展示房间列表，关闭后恢复完整聊天宽度。[RightPanel](../../apps/web/src/components/RightPanel.tsx) 不能只依赖 `hidden xl:flex`，否则轨迹按钮在窄屏缺乏明确可见的目的地。现有任务卡内联审批应继续保留，不需要为了缩减配置而隐藏待处理事项。

### U05：让用户理解自己将要发给谁

新房间同时展示一排“候选团队”和一排“本轮对象”，例如选中了鸡腿作为房间成员，又可以在下一排再次选择 `@鸡腿`。目前按钮主要展示名称和颜色，职责、模型接入、是否只读等只能在别处了解。新房间还默认选择所有已启用角色，用户可能把入房理解为本轮全部执行。

建议使用明确的文案与位置：房间成员在房间设置中维护；输入框附近显示“接收人：自动选择”或明确成员。成员选择器展示头像、名称、职责与可用状态，选中同时使用勾选和文字反馈。正文 `@` 提供候选补全，并与接收人选择保持一致；发生冲突时在提交前解释。

策略和工作流是不同层次，保留现有契约，但普通用户先看到“常规协作、并行分析并汇总、开发并评审、主管拆解、辩论”等场景及一句话说明。高级用户可展开独立选择策略、工作流、角色及约束。不可用组合说明原因，不能通过静默切换改变用户意图。

普通引用回复应显示“回复 鸡腿 · 将创建新任务”之类的上下文；等待问题时显示“回答并继续第 N 轮”；安全暂停后的修订显示“补充第 N 轮 · 保持暂停”。这些文案应反映现有后端行为，不能仅靠按钮改名把新任务伪装成原任务续接。

### U06–U08：失败和任务上下文需要可理解

实际失败房间展示“阶段 B 写入须选择已注册的 Git 仓库工作区”“Completion Engine 拒绝完成”“执行尝试租约已失效”等信息。用户需要从系统消息与执行尝试中找最初的可操作原因。当前任务详情主要指向消息和轨迹，没有把“修复配置后怎样继续”串起来。

建议任务卡先说明直接原因，例如“本任务需要 Git 工作区，当前房间使用自动工作区”，再给可行操作，例如“带原目标新建房间并选择仓库”。已确认成果单独展示；错误码、责任租约及技术日志放入“查看技术详情”。不支持重试的工作流应如实说明，提供携带原目标、接收人和设置的新任务草稿，不能显示无法兑现的“一键恢复”。

检查面板的终局、预算和执行尝试按当前任务过滤，但调度列表直接渲染整个房间的 `collaborationDispatches`。应统一上下文，并在选中不同任务时给明确标题与高亮。刷新则应保持选中房间，不应无提示回到最新房间。

### U09–U14：完善可发现性与视觉层级

- 房间 `•••` 应打开菜单，归档放在明确的菜单项中并继续保留确认。重命名目前依靠双击列表，应增加可发现的入口，并给保存失败反馈。
- 手机回复入口默认透明；应常显或通过消息菜单进入，并扩大触控区域。键盘也应能清楚识别当前焦点和操作对象。
- 已完成任务卡可以默认呈现“第 N 轮 · 已完成 · 简短目标”，展开再看路由原因和计划。保留审批、提问、失败和暂停等需要处理的卡片。
- 聊天正文、最终成果、协作过程和系统诊断要有不同的视觉权重。角色颜色用于身份识别；状态色采用一致语义，避免所有层次都使用同样的暗灰卡片。
- 将默认检查面板中的 `Dispatch / Attempt / generation / accepted / fanout` 等转换为易读名称；原始值保留在技术详情。未知用量和费用应交代统计口径，避免与零消耗混淆。
- 长代码支持逐块复制，长报告支持展开和定位，引用跳转增加短暂高亮。现有 Markdown、代码及表格滚动能力应保留。
- [ChatScrollController](../../apps/web/src/chatScroll.ts) 已尊重用户手动翻阅，但缺少离开底部后的新消息提示；增加提醒和主动回到底部，不要恢复无条件强制滚动。
- 首屏数据尚未加载时会短暂出现创建房间和“暂无匹配聊天室”，随后才切到已有房间。使用加载骨架或明确状态，并区分无房间、搜索无结果和加载失败。
- 输入框是多行，但 Enter 会提交。保留现有中文输入法 `isComposing` 处理；建议提供 Enter/Ctrl+Enter 发送偏好，发送说明放在输入框附近，长任务编辑时减少误提交。

## 预期的日常交互

1. 打开房间：保留上次选择和阅读位置，主要看到消息；头部只有名称、成员、当前状态和详情入口。
2. 输入任务：写目标，接收人默认自动选择；需要指派时输入 `@` 或打开成员选择器。
3. 调整协作：点击“执行设置”选择场景，按需展开策略、评审者、只读约束和预算；当前设置以简短摘要返回输入区。
4. 查看执行：点击任务卡的详情入口，打开所选任务的检查面板，消息历史保持完整。
5. 需要处理：待审批、用户问题、执行失败以清晰卡片及可行操作呈现，不让用户搜索底层日志。
6. 手机切换房间：打开覆盖式列表，选择后关闭；设置和执行详情通过独立面板查看。

## 建议实施顺序与验收标准

第一批修复 U01、U07、U08，保证消息和任务上下文正确。验收应覆盖多任务房间切换轨迹、引用定位、刷新和异步回填，不能只测单任务房间。

第二批处理 U02–U06、U09，形成紧凑输入区、清晰接收人、失败恢复入口及响应式抽屉。建议将以下尺寸作为设计目标，而非现状或标准合规声明：桌面默认消息区占房间内容高度至少 55%；手机软件键盘关闭时至少 50%；打开房间列表不缩窄聊天列；设置展开时有独立、明确的滚动区域。

第三批统一 U10–U14 的视觉、术语、成果阅读和键盘行为。补充 390、768、1024、1279、1280、1440px 验收；不仅检查横向溢出，还检查消息区域实际尺寸、触屏按钮、软件键盘、长消息、代码表格及待处理事项可达性。

保留现有任务编排、账户绑定、权限、独立评审和安全暂停语义。UI 场景预设应映射到已有契约，不重新增加独立执行入口。
