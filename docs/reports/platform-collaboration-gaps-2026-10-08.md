# agent-gand 长链路协作能力差距分析

日期：2026-10-08。代码基线：`1136ea21299aa6ced73a629433586ee3c425c81e`。

整改跟踪：[Issue #14：完善长链路多 Agent 协作](https://github.com/cat15926/agent-gand/issues/14)。

本报告以最近一次真实混合后端聊天室测试为入口，复核统一编排入口、Collaboration、Coordination、Runtime、外部执行、消息与上下文、预算和任务交互。它是本地证据支持的差距分析，未进行新的供应商推理、业务数据修改或产品代码修改，不代表全部生产场景已经验证。

## 结论

平台已经具备账户与角色快照、执行权绑定、责任代际、幂等提交、工作区隔离、持久化等待和完成门禁。最新测试证明 Claude SDK 与 Codex 可以共同参与协作，也暴露出长链路协作的正确性、恢复和资源治理尚未形成完整闭环。

主要差距是：消息接收者未形成信息可见性边界；常规任务缺少结构化阶段与业务验收；失败后的续跑能力在引擎之间不一致；超时配置分散且混合计时；外部用量未知未进入协作预算政策；诊断记录缺少因果层次。改进应落在统一任务契约与公共 Runtime 能力上，可用于编码、调研、评审、讨论和其他有状态流程。

数据通过 SQLite 只读连接读取；未读取账户凭据、登录文件或完整私有原生日志。

## 当前已有能力及实际边界

| 能力 | 已存在的基础 | 本次反映的边界 |
|---|---|---|
| 统一编排入口 | 目标、策略、工作流、账户能力快照与执行权威 | 常规复杂请求仍可能直接进入动态协作，缺少阶段、信息约束与完成条件的任务契约 |
| 执行安全 | Attempt、租约、代际、原生进程归属、工作区隔离、迟到结果隔离 | 安全停止后，用户承接已确认进度的路径不足 |
| 持久状态 | Subject、Custody、Obligation、Capsule、Hold、Checkpoint | 调度状态不能自动表达业务阶段、事实、规则、参与者状态和最终目标 |
| 完成验收 | 依赖、后继义务、输出、证据、评审与协议门禁 | 常规 Collaboration 没有任务专属验证器时主要验收执行结构与结果存在性 |
| 暂停与恢复 | 用户决策唤醒、安全暂停恢复、重启收敛、部分任务重试 | 不同引擎的失败恢复范围不同；失败自由协作缺少关联续跑入口 |
| 用量与观测 | 记录 unknown、首文本时间、Span、错误、预算快照 | 协作预算仍只累计已知用量；超时阶段与错误因果不够清晰 |

## 问题 1：定向投递与信息可见性没有形成共同契约

**性质：已发生的信息隔离缺陷，优先级 P0。**

`messaging/inbox.ts:134` 按聊天室读取全部消息；`runtime/context.ts:136` 读取整个聊天室，`:185` 的最近消息筛选排除了贡献消息，但仍保留咨询正文和包含贡献原文的系统汇总。当前 `to` 指定调度接收者，未形成收件者专属的上下文可见性。

这会影响独立调研、盲评、分别报价、角色持有不同信息、仅发给主管的报告等场景。脱敏 API Key 不能替代对业务内容的可见性控制。此次问题是 Agent 之间的信息边界，不能据此宣称存在已证实的跨租户泄漏。

另外，模型把现有咨询工具描述为“秘密通道”，平台未提供这项语义。需要同时解决能力声明和信息隔离：尚不支持私密消息时应明确约束模型的承诺；支持后应通过结构化 visibility/audience 表达。

改进边界应覆盖原始消息、咨询结果、聚合摘要、Capsule、证据摘录、检索、原生会话恢复和面向不同观察者的 UI/事件。不能只过滤主聊天列表，或仅按 `to` 隐藏所有消息，因为定向投递也可能是允许全队查看的公开指派。

## 问题 2：常规任务契约尚未表达业务阶段与成功条件

**性质：代码确认的能力缺口；本次未发生错误成功判定，优先级 P0/P1。**

本次冻结请求为 `routine + auto`，明确只指派鸡腿，进入 `dynamic_collaboration`；没有 Coordination Plan。尊重明确指派本身是正确行为。问题是任务的多阶段、信息不对称和终局条件均由模型在自由文本中维护。

`orchestration/resolver.ts:97` 对若干已知工作流做规则识别，`:123` 的自动执行者选择优先取可用成员。它可保证基础准入，但当前请求路径缺少对阶段数、消息信息约束、验收方式与预期调用规模的通用评估。

`runtime/subjectCompletion.ts:271` 在 Collaboration 适配提交中将 dependencies、requiredArtifacts、reviewAccepted、protocolTerminal 作为成立项传入；其他责任与证据门禁仍会执行。因此不能说“没有完成门禁”，但常规流程缺少领域验证器时，非空结果和执行结构正确不能证明原始目标已经完成。Coordination 开发评审已有独立 PASS/FAIL 和返工门禁，应保留并扩展其可验证契约。

业务状态建议包括当前阶段、规则与约束、已确认事实、必要参与者、待满足条件、阶段产物、可公开摘要和受控私有状态；使用版本与事件来源维护。Runtime 调度状态与业务状态关联，而非让平台硬编码每一类游戏或业务。

另一个房间中，用户说“我不加入了，结束游戏吧”，Agent 收尾后 Run 为 completed/accepted，正式游戏仍未开始。最新用户请求确实被处理，不能据此直接认定运行状态错误；它说明产品还需区分“请求处理结束”“原目标达成”“用户提前结束”和“接受部分结果”。

## 问题 3：安全恢复与可继续交付之间存在缺口

**性质：代码和本次结果确认，优先级 P0。**

Collaboration 捕获执行异常后结束 Attempt 并调用终局判定；本次一次主持人超时使 Run 直接进入 failed。

已有恢复机制会收敛旧原生进程、保留证据、拒绝重放不确定副作用，这些约束是必要的。`execution/recovery.ts:6` 明确不会重新启动模型。主管任务的 `orchestration/actions.ts:83` 已支持分支重试并复用确认结果，但 `:89` 限定了适用范围。Coordination 有步骤级重试。不能把“Collaboration 缺少失败续跑”概括成整个平台没有恢复或重试。

任务卡对失败自由协作提供“准备新任务草稿”；`RunView.tsx:323` 复制目标与设置，没有恢复业务阶段和已确认状态。保存旧消息有利于审计，但用户依旧需要手动重建执行进度。

需要统一错误类别与恢复资格：可确认无副作用的暂时性错误、等待外部条件、结果未知、明确业务失败、用户取消应有不同处理。对结果未知或写入调用先收敛进程、检查工具账本与实际产物；不得默认重跑。可通过终态前的 needs_attention，或终态后的关联续跑 Run 实现承接，保持旧终态不可变、新 Attempt/代际可追踪，已确认步骤不重复执行。

## 问题 4：超时来自多层配置，时间语义未统一

**性质：本次直接触发；其他影响为代码确认的风险，优先级 P0。**

- `orchestration/agentStep.ts:249` 使用全局 external timeout 与 Run deadline 的较小值，在成员准入和工作区准备之前启动计时。
- `execution/runner.ts:104` 又使用账户 timeout；部分 Coordination 调用还受步骤租约约束。
- `execution/rpc.ts:73` 再设置原生进程 timeout。

本次账户 timeout 为 180 秒，外层单轮计时触发。仅增大账户 timeout，仍可能被全局外层限制中止。排队和工作区准备也占用单轮预算，在高并发场景会出现“模型尚未开始，执行时限已消耗”的问题；本次排队很短，不能把该风险当作已发生原因。

建议冻结一份可解释的 effective timeout policy，明确 Run deadline、队列等待、进程初始化、首响应等待、无进展等待、Attempt 最大时长与步骤时限。Run deadline 可覆盖全部等待，模型执行预算应有明确起点；只根据可信进度更新无进展计时，不因普通心跳无限延期。

## 问题 5：调度粒度与推理成本不匹配

**性质：本次实测确认，优先级 P1。**

报名和发牌消耗 11 分 19 秒、15 次派发，正式业务尚未开始。确认消息、串行征询和主持人聚合均触发完整外部调用。咨询工具支持一个 objective 加多个 targets，适合共同问题的并行咨询，不表达对不同接收者分别投递不同私有内容的批处理。

主持人的 7 次调用全部为 cold。`runner.ts:230` 仅在自然结束且无控制动作时将原生会话标为可安全复用。控制动作会结束回合，这是有意维护执行边界的机制；不能直接放宽为无条件复用。

改进方向是让服务端处理确定性的确认、状态迁移与汇合，让模型用于需要判断和表达的工作；提供受可见性约束的差异化批量任务和阶段结果；根据任务规模预估派发预算，并在阶段边界重新评估。原生会话复用必须同时满足账户、角色、工作区、权限和信息可见性绑定。

## 问题 6：未知用量与预算治理使用不同语义

**性质：代码与真实数据确认，优先级 P1；涉及严格额度承诺时应作为准入条件。**

本次 13 次 Claude SDK 调用用量均未知，只有 2 次 Codex 的 34,340 tokens 被计入。`collaboration/store.ts:470` 对 Span 的已知 tokens/cost 求和并将空值聚合为 0，随后按该值判断预算。

执行详情、顶栏与观测页面已经能显示“未知”，因此问题不是所有 UI 都把未知写成 0，而是预算政策没有跟随该语义。SDK 调用在收到控制动作后提前结束，与仅在原生终局获得完整用量的统计方式存在冲突；当前记录不能提供真实整场成本。

能力准入已将外部后端的 hardTokenLimit 标为 false，并拒绝部分严格 token 限制，应保留。进一步统一已知实测、估算/预留、未知、计价未知四类状态；明确哪些后端支持硬限制，哪些只能做近似治理。未知不应被视为零消耗，也不能把估算显示为供应商真实账单。

## 问题 7：错误记录缺少因果、阶段和可执行解释

**性质：本次实测与代码确认，优先级 P1，宜与超时修复一起处理。**

超时、不可提交、租约失效被并列展示，用户难以识别原始触发点。最后调用已经初始化会话，但未收到文本与工具事件；现有记录仍不足以区分供应商请求等待、SDK 内部等待和传输状态。

`runner.ts:247` 将未收到结束事件的工具 Span 标为 error，即使 execution 已 completed；本次有 12 条这样的记录。它们应表达为受控中断后的完成事件缺失或待解释状态，不能直接当作已确认工具失败，也不能伪造工具正常完成。

另一次真实执行桥 HTTP 400 发生在最终成功的初始调用中。`bridge.ts` 返回诊断正文，但 `bridgeWorker.ts:14` 只向模型返回 HTTP 状态，丢失具体校验原因，降低纠错效率。

建议建立结构化诊断：主原因、衍生状态、可恢复资格、执行阶段、最近可信进度、有效时限、已确认结果和下一步动作。持久保存必要的脱敏诊断与 request ID；原生 stderr 在超时路径只保存在进程内缓冲不足以支持事后调查。用户默认看到可理解摘要，技术细节展开查看。

## 问题 8：验收覆盖与真实长链路使用存在差距

**性质：现有验收范围确认；不是此前测试无效，优先级 P1。**

O7 及外部 Agent 的本地验收通过真实 HTTP/进程协议使用 fixture；真实账户最小任务是独立空房中的单人只读请求。`docs/architecture/orchestration-entry-phase-o7.md:40` 明确了其范围。已有恢复故障测试验证不重放未知原生副作用，但不能据此推导混合供应商、多阶段、信息隔离与长时间协作已通过。

验收需要在可控故障注入基础上，再覆盖少量经授权的真实混合后端多阶段任务，并分别记录正确性、恢复、时延、未知用量比例和人工干预。真实供应商请求不应作为默认每次提交的测试；使用隔离数据和明确执行入口。

## 建议实施顺序与验收标准

这些是待评审建议，没有在本次分析中实施。

| 顺序 | 改进项 | 可评审的验收标准 |
|---|---|---|
| 1 | 信息可见性契约与能力声明 | 两名成员获得不同私有信息；另一成员的消息、汇总、证据、会话上下文中均无越权内容；公开指派仍可正常共享 |
| 2 | 统一超时与结构化诊断 | 账户/全局/步骤时限的有效值可解释；队列等待与模型执行分别计时；无首响应和执行后停滞显示不同原因；受控中断不增加已确认工具失败数 |
| 3 | 公共恢复资格与关联续跑 | 注入中间超时后保留确认阶段；重复续跑请求只产生一个恢复执行；无重复工具副作用；旧终态与证据不被改写 |
| 4 | 阶段状态、业务验收与目标结果 | 编码、调研、评审等不同流程均可表达阶段和产物；只收到确认不能通过必要交付验收；用户提前结束与原目标完成有可区分记录 |
| 5 | 调度优化与预算一致性 | 确定性确认无需额外完整推理；同一目标的并行与差异化任务尊重信息边界；未知 SDK 用量不会被预算当作零；限制类型在预览可见 |
| 6 | 跨引擎回归与真实长链路验收 | 同一任务在合适的引擎上具备一致的可见性、超时解释、确认结果和恢复资格；混合后端流程遇到故障可解释、可继续或明确结束 |

## 必须补充的回归场景

1. 定向公开任务与私密任务的可见性差异，包含聚合、Capsule、检索与会话恢复的负向断言。
2. 混合 Claude SDK/Codex 的多个阶段，中间调用超时，确认产物保持不变。
3. 无文本但存在原生工具/可信进度的长调用，与完全没有进展的调用。
4. 同一 Agent 在多个聊天室排队，队列预算与 Run deadline 按各自契约处理。
5. 控制动作已持久提交但工具终局事件缺失；真正工具失败和校验拒绝另行分类。
6. 用量全部未知、部分未知、成本价格未知及严格预算不受后端支持的准入。
7. 模型提交完成候选但缺必要业务产物；独立评审 FAIL 继续阻断交付。
8. 用户主动提前结束、接受部分结果、业务成功三种结果的清晰呈现。
9. 重启或断网发生在提交响应前后；幂等恢复，不自动重放未知写入。

## 需要保留的工程约束

沿用统一入口和冻结策略，不为每个业务新增顶层协作模式；保留旧终态不可变、代际隔离、消息幂等、工具账本、独立评审、原生进程归属和工作区隔离。增加自动恢复必须基于可确认的安全边界。延长超时可作为受预算约束的参数调整，但不能替代信息隔离、进度承接和真实业务验收。
