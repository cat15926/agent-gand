# 逐阶段执行与用户验收门禁 v1

在现有[业务验收契约](./business-acceptance-v1.md)上增加按任务启用的执行方式，复用 Coordination DAG、Runtime 执行绑定与 Owner 验收账本。没有 `executionMode` 的旧契约继续执行结束后验收，不改变原任务派发。

## 用户操作

1. 打开任务的“执行设置”，启用阶段验收，将方式切为“逐阶段执行 · 验收后继续”。界面切到常规顺序工作流；接收人改由阶段任务指定。
2. 每阶段填写名称、具体成员任务、必要交付和验收标准。阶段内任务按列表顺序执行，同一阶段成员不可重复；后续阶段可再次使用同一成员。总步骤（包含验收及最终门禁）不超过 64 个，整张图最多 12 位成员；顺序阶段不受动态协作单次接收人数量限制。
3. 可选设置阶段执行时限和阶段输出 Token 总预算，预览确认所有阶段的分工、依赖和预算，再提交执行。当前支持模型 API、Claude SDK、Codex app-server；只读 CLI 会给出不可执行原因。
4. 当前阶段全部成员交付后，任务停在“等待你的处理”。展开“查看计划、结果与验收”，关联当前阶段的完成输出，或核对当前计划工作区文件，逐项确认标准。
5. 点击“验收通过并继续执行”后，平台继续派发下一阶段，可能消耗模型额度。拒绝候选保持暂停，可以重新核对证据并登记；不会自动重跑。普通“恢复”不能绕过未验收门禁。
6. 最后阶段验收后完成最终执行检查。业务验收结果和执行终态分别显示。提前结束需先取消；可继续验收取消前已完整交付的阶段，再接受部分结果，取消后的任务不会重新启动。

## 冻结数据

```json
{
  "version": 1,
  "executionMode": "stage_gated",
  "stages": [
    {
      "id": "analysis",
      "title": "分析方案",
      "criteria": ["原因与边界清楚"],
      "deliverables": [{"id": "report", "title": "分析报告", "kind": "text"}],
      "execution": {
        "assignments": [{"agentId": "analyst", "objective": "分析失败原因，交付方案与风险边界"}],
        "timeoutMs": 300000,
        "maxTokens": 8000
      }
    }
  ]
}
```

所有成员必须在候选团队内且账户可用。阶段分工、预算和门禁参与预览指纹，确认漂移会拒绝提交；阶段模式不允许用修订图重放已有阶段。阶段清单和分工不写入房间默认，草稿可以保留未填写完整的内容。与全队、回复定向及辅助角色路由冲突时，预览会要求明确调整。

## 调度与确认

编译阶段任务为 `agent_turn`，每阶段结尾插入带 `businessAcceptanceGate` 的 `completion_gate`；下一阶段依赖前一验收门禁。失败步骤只有一次执行尝试，不会因阶段失败隐式返工或自动重放。平台派发确认来源于已认领的持久化 Attempt 和阶段起始记录，表示任务已派发，不代表模型说过“收到”或完成了业务目标。

门禁到达 ready 后先暂停 Run/Plan，不创建正在运行的假 Attempt，也不调用模型等候验收。当前阶段清单与分工注入 Agent 上下文；后续阶段分工不进入当前回合。前序完成输出按现有依赖关系提供。

Owner 验收仍通过 `/api/accounts/business/:runId` 的管理会话、CSRF 与来源校验提交，保留版本 CAS、请求幂等和追加审计。验收前核对必要证据及哈希，且要求没有运行进程、工具、Attempt、未知调用或未收敛副作用。阶段文本证据必须是同 Run、同计划版本、当前阶段的已完成成员 Attempt；[阶段续跑检查点](./business-stage-continuation-v1.md)显式归档的同阶段完成输出也可引用。普通消息、未授权的其他 Run、其他阶段结果和门禁输出不能替代。文件证据在当前门禁收敛后采集，绑定计划工作区 Scope 和内容哈希；文件 API 需提交 `stageId`，验收时重新核对。

接受决定提交后由原 Coordination 执行器继续，终态不被改写。提交成功后若 HTTP 唤醒前崩溃，启动恢复和每秒持久化恢复扫描会识别已接受的暂停门禁；进程内执行锁及已完成步骤防止重复调用。未接受、被拒绝、被取消、有未知结果的任务不会自动启动。暂停门禁可通过同一接受请求幂等重试，或在已验收后普通恢复。

## 阶段预算

阶段时限从第一个成员 Attempt 被派发时开始，后续成员共用同一个起始时间；成员排队、准备、工具和普通暂停均计入。到达验收门禁后阶段执行结束，等待用户验收不占下一阶段时限。Run 的冻结总截止时间持续计时，也包含用户等待；不能通过阶段转换延长它。

阶段输出 Token 预算累计所有成员、模型调用及工具轮次的输出，只允许支持输出硬限制的模型 API 成员。阶段与 Run 的输出预约在一个数据库事务中共同认领，不能被并发重复消费；实际使用回填，缺少 usage 按全额保留，未知调用保留预约且禁止后续自动调用，已接受门禁的普通恢复同样受此围栏约束。执行终态的业务结束仍核对进程与工具副作用是否收敛；只有调用消耗未知时，允许用户明确结束业务验收，保留输出额度并持续显示未知消耗。SDK/app-server 不能落实输出 Token 硬上限，预览会拒绝该配置；可使用阶段时间限制。输入 Token 和货币费用不包含在此预算中。

新增 `business_stage_executions`、`business_stage_token_reservations` 两张表；追加编排迁移 v3。旧 worker 无法识别验收门禁，已有迁移保护会拒绝打开 v3 数据库，避免降级后自动越过门禁。发布前按现有备份流程保留数据，已启动的旧任务采用原冻结契约。

## 验证与后续范围

`pnpm verify:business-stage-gates` 使用临时 SQLite、Git 工作区、API mock、本地 SDK/Codex stdio 模拟进程和 Fastify 注入，不请求真实模型，不监听端口。覆盖派发顺序、后续阶段上下文隔离、拒绝与普通恢复围栏、阶段证据、HTTP 接受自动继续、CAS/幂等、接受后崩溃恢复、取消不复活、时限、并发与未知输出预算、冷进程读取和降级保护。另以 `--kernel-off` 验证兼容执行路径。覆盖原生写入前审批、文件哈希漂移和后续 Codex 超时保留已验收阶段。

`pnpm verify:business-stage-gates-ui` 验证完整任务编辑 → 预览 → 交付登记 → 勾选标准 → 接受后继续 → 两阶段完成的真实页面操作；包含 390px 布局检查和截图。先运行 Web 构建；沿用其他 UI 脚本的可选 `PLAYWRIGHT_MODULE` / `CHROMIUM_EXECUTABLE_PATH`。浏览器使用全新临时资料，页面及 API 请求由静态构建和 Fastify 内存注入响应，WS 事件由内存总线转交，不监听端口。此夹具验证页面交互，不替代真实网络、WebSocket 传输或真实模型验收。

公开只读阶段的跨 Run 验收继承、确认输出归档和必要交付文件迁移见[阶段续跑检查点 v1](./business-stage-continuation-v1.md)。拒绝交付后的明确返工已通过[公开只读阶段返工 v1](./business-stage-rework-v1.md)接入。私密/写入阶段返工、多分支跨引擎续跑、写入工作树迁移、货币费用硬预算仍是后续范围。
