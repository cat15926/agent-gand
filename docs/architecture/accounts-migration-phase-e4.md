# 阶段 E4：账户迁移、运行恢复与回滚

状态：本地实现与验收完成，日期 2026-10-05。真实供应商授权、模型权限及计费链路仍需用户验收，见 [E4 验收记录](../reports/accounts-phase-e4-acceptance.md)。

## 兼容与迁移规则

启动时沿用幂等 schema 初始化，新建账户相关表及缺失字段。E4 增加 `run_planner_snapshots`：每个新 Run 保存独立规划器的 ID、模型和账户引用；`definition=NULL` 表示使用该 Run 的团队规划者。表中没有 Key、Token 或登录目录。

现有角色缺省 `accountRef` 时继续使用原有 `.env` 或专用 CLI 来源；文件角色依旧由 Markdown 定义，不自动写回文件或把环境 Key 导入数据库。内置 Anthropic 与 Claude SDK 的旧 Key 来源保持独立。新建真实角色明确选择账户；带 `requiresAccount=true` 的未绑定草稿不能被当成旧环境角色。

已有 `run_agent_snapshots` 逐字保留。缺失成员优先使用 `agent_versions` 中 Run 创建时间之前的最新版本，部分快照只补缺失成员。缺少历史版本时，仅保留原有旧来源的兼容回填行为。如果角色已经选择托管账户，却没有可确认的冻结绑定，不推测当时的账户，不生成历史凭据版本。绑定与角色来源不匹配时也不回填。检查命令会报告这些缺口；恢复路径在成员不完整时停止运行，避免执行缩水的团队。

旧 Run 不补写规划器来源。其规划仍可使用旧环境配置，或从已有角色快照选择团队规划者；不会因为升级后的独立规划器改为托管账户而引入这个新账户。

## 调用与冻结

新 Run 在创建事务内保存成员配置及托管账户的连接版本、凭据版本或登录身份代次。独立规划器使用内部 ID `system:coordination-planner`，与用户角色 ID 不冲突，并纳入账户引用和撤销检查。可选规划器在创建时不可用不会阻止手动运行，其缺失绑定也不会在稍后修复账户时自动补齐；智能规划安全回退。

运行中的结构化追问和计划修订使用当前 Run 的成员、模型及规划器快照。普通回合、主管单次调用、审查协议和工具预算收尾均通过 `providerForAgent(agent, runId)` 解析认证。即使传入的角色意外丢失 `accountRef`，已有冻结绑定也会阻止回退到全局 Key。旧环境 Key 的值仍遵循旧环境配置语义，不宣称具有托管凭据的历史版本冻结能力。

轮换 Key、修改地址、换绑角色和停用账户只影响新 Run；已排队 Run 使用原版本。立即撤销使依赖运行停止。身份冻结的是登录代次，客户端仍可刷新 Token；不能自动换成另一账户继续。

## 只读检查

```bash
pnpm accounts:audit
```

工具读取与服务相同的 `.env`、`DB_PATH` 和目录配置，直接以只读模式打开 SQLite，不导入自动初始化模块。即使检查升级前数据库，也不建表、不登录、不探测 CLI、不发模型请求。退出码 `0` 表示检查通过，`2` 表示报告中存在需处理的迁移/配置问题，`1` 表示工具无法运行。

报告只含计数、问题代码、账户/角色/Run ID 和版本。检查覆盖数据库完整性、主密钥权限与密文校验、当前账户指针、活动运行需要的凭据/身份、缺失或不匹配的快照/绑定、登录目录存在性、未绑定草稿。已终止 Run 删除历史凭据后的归档状态不会被误报为活动恢复错误。检查不会刷新或确认原生 Token，也不能证明供应商模型权限有效。

常见问题：

| 问题代码 | 处理 |
| --- | --- |
| `MIGRATION_PENDING` | 先完成停机备份，再启动新版本执行幂等迁移，然后重新检查 |
| `MASTER_KEY_UNAVAILABLE` / `CREDENTIAL_LOCKED` | 恢复原主密钥及匹配数据库，检查权限；不要生成新主密钥或 reset |
| `RUN_SNAPSHOT_MISSING` / `RUN_BINDING_MISSING` / `RUN_BINDING_SNAPSHOT_MISMATCH` | 对照完整旧备份核实来源；不能把角色现在的账户填入历史 Run |
| `RUN_CONFIG_MISSING` / `RUN_CREDENTIAL_MISSING` / `RUN_IDENTITY_MISSING` | 恢复冻结版本或停止无法恢复的运行；不要替换账户后重放 |
| `IDENTITY_DIRECTORY_MISSING` | 恢复匹配身份代次的私有目录；如已失效，由用户重新授权并用于新 Run |
| `ENABLED_ROLE_UNBOUND` / `ROLE_ACCOUNT_MISSING` | 在向导中停用并修复角色，再创建新 Run |

## 停机备份

先正常停止服务并等待原生进程清理完成。备份输出的父目录必须已经存在，输出目录必须是新的目录：

```bash
mkdir -p apps/server/data/backups
pnpm accounts:backup --output apps/server/data/backups/accounts-20261005
pnpm accounts:verify-backup --input apps/server/data/backups/accounts-20261005
```

备份工具使用 SQLite backup API 获取含 WAL 已提交数据的一致副本；同时复制整个账户私有目录、配置的专用 Codex/Claude 旧目录、文件角色目录与头像。目录权限 `0700`，文件 `0600`。清单包含恢复原路径、schema 校验和、Git HEAD/工作区是否变化以及每个文件的 SHA-256；工作区有未提交变更时，HEAD 不能代表当前完整实现，必须另行保留对应源码。

存在活动服务所有者、未清理原生进程、未结束登录或测试时拒绝备份。备份期间数据库变化、缺少可验证主密钥/已认证身份目录、链接或特殊文件也会中止，并清理本次不完整输出。不覆盖已有备份。`verify-backup` 只读核对权限、普通文件、文件清单、大小和校验和；这些校验用于检测损坏，不是外部备份的真实性签名。

使用 `ACCOUNT_MASTER_KEY` 的部署必须通过原有安全渠道另行保留原值，备份不会导出该环境变量。备份也不会导出 `.env` 中的旧供应商 Key。原生目录中可能包含 OAuth 认证材料，整个备份应由原账户所有者保管；不要上传到仓库或作为报告附件。默认 data 目录已被 Git 忽略，备份还包含自身 `.gitignore`。

该工具是账户及运行数据库的备份。完整业务回滚还应另行保存 `.env` 部署配置、sandbox、外部工作树/产物、注册的项目目录、依赖及对应源码版本。工具不复制用户个人 `~/.codex` 或 `~/.claude`，除非用户曾明确把它配置为项目专用目录；通常应使用默认专用目录。

## 回滚步骤

1. 正常停服，取消未结束登录/测试，确认原生执行已清理。先对当前状态再做独立备份，避免覆盖升级后成果。
2. 用 `accounts:verify-backup` 核对拟恢复备份，查阅 `manifest.json` 的 `sources[].restoreTo`、`application` 和 `externalMasterKeyRequired`。不要把来源未知的清单当作可执行恢复指令。
3. 保留当前数据库、WAL/SHM 和相关私有目录作为整组回退副本；将备份 `database.sqlite` 恢复到清单指定的原数据库路径。不要将旧数据库与新 WAL/SHM 混用。
4. 将 `private`、`legacy-codex`、`legacy-claude`、`roles`、`avatars` 中实际存在的项目分别恢复到清单中的原路径；目录 `0700`、私有文件 `0600`，归属服务运行用户。原生身份表保存绝对路径，本轮只验证原路径恢复，搬迁目录需要单独设计迁移。
5. 恢复匹配的原 `ACCOUNT_MASTER_KEY`（若使用环境提供），部署配置、源码和业务工作区。回滚到 E1 之前版本时，使用升级前的数据库/角色/旧认证来源整组备份；旧版本不会使用新托管账户，不应把托管 Key 明文导出到 `.env`。
6. 先运行 `accounts:audit`，再启动服务。核对角色/历史 Run 数量、账户解密状态和排队恢复结果；认证失效的原生账户由用户重新授权。已明确失败或无法证明安全的外部业务执行不盲目重放。

E4 自动测试在临时原路径完成数据库、主密钥和原生目录恢复演练，并验证缺主密钥、清单篡改、活动服务和遗留进程都会被阻断。没有替换本地用户数据库或停止其开发服务。
