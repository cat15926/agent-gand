# Agent 自主协作与单一任务入口实施方案

状态：**待评审，尚未实施**。日期：2026-10-17。

本方案根据用户最新要求调整产品目标：用户向自己的 Agent 提出需求，由 Agent 组织协作并交付结果；用户不负责拆分材料、选择批次、搬运结果和逐条批准内部消息。本轮仅交付方案与交互预览，不修改运行逻辑、服务配置、权限或历史任务。

既有 G0–G6 提供可复用的隔离、调度、恢复及披露机制。此前承诺的是固定计划和人工授权入口，并未完成本方案的自主产品流程；[SDK 接入收尾报告](../reports/scoped-collaboration-native-integration-2026-10-17.md)中的通过记录不能替代本方案验收。

## 1. 评审结论与产品目标

推荐采用 **用户提需求 → 主 Agent 组织任务 → 平台执行与约束 → 自动交付** 的默认交互。

| 用户当前承担的工作 | 改造后的责任方 | 用户看到的内容 |
|---|---|---|
| 选择组织者和每份材料的接收者 | 被用户指定或房间默认的主 Agent 选择合适成员 | 谁负责、正在做什么 |
| 手动拆分并填写逐人材料 | Agent 形成任务，Runtime 按授权编译各自输入 | 可展开的分工记录 |
| 决定批次与等待关系 | Agent 提出依赖，Runtime 排队、并发和唤醒 | 当前步骤与真实等待原因 |
| 查看结果并复制给下一个成员 | Runtime 保存来源，按任务权限传递给后继或汇总者 | 交付进度和结果 |
| 逐条预览、确认汇总和内部发布 | 服务端在本任务授权内自动执行 | 持续进展和最终交付 |
| 判断模型是否真的发出任务、完成文件 | Runtime 核验 Dispatch、工具回执、证据和完成条件 | 可核对的完成或失败说明 |
| 处理每次局部失败 | Agent 与 Runtime 在规则内重试、调整分工或说明阻塞 | 仅无法继续时出现一张决策卡 |

普通任务在已有账户、成员、预算和工具权限内直接执行。缺少关键业务信息时合并提问；涉及扩大访问范围、任务预算或未获明确授权的外部操作时，针对实际动作请求决策。用户已经明确授权且策略允许的动作不重复询问。内部委派、收集、汇总和允许范围内的结果返回不逐项弹窗。

**权限应由用户的任务授权和房间设置决定，Agent 在该范围内做事；平台负责裁定。** 不把管理会话、CSRF 或 Owner 签发能力交给 Agent，也不通过后台伪造用户点击来实现自动化。

## 2. 预期交互

### 2.1 默认输入区

保留普通聊天输入框。用户可以 `@某个 Agent`，也可以使用房间默认接待 Agent。没有必要再创建一个专门的“组织者”角色。

- 主操作：输入需求、上传相关材料、发送。
- 可选：指定主 Agent、限制可参与成员或设置本轮预算；未改动时使用房间默认值。
- 当前“独立材料协作”表单移入“高级 → 手动编排”，作为专业操作、诊断和兼容入口保留。
- 默认不展示批次、Scope、Manifest、信封、发布 Grant、后端协议等实现字段。
- 不要求用户先判断普通协作、静态阶段、私密材料等引擎模式；服务端按需求和可用能力准入。

“发送”意味着在页面清楚展示的任务默认范围内开始工作，不再为同一次普通提交增加通用确认页。房间默认范围可一次设置，此后沿用；本轮发生实质越界时再请求决策。

### 2.2 执行中的任务卡

示例请求：“请评审这份方案，分别检查实现可行性和测试风险，合并意见并修改报告。”

```text
你：请评审方案，检查实现与测试风险，合并意见并修改报告。

鸡腿：我会请两位成员分别审查，再核对分歧并更新报告。

正在协作 · 鸡腿负责
已完成：拆分任务
进行中：实现审查、测试审查
下一步：核对分歧 → 更新报告 → 交付

[展开协作过程]  [暂停]  [停止]
```

执行叙述来自已提交的计划与执行回执。没有创建任务不能显示“已委派”，没有有效待办不能显示“等待成员回复”。默认展示简洁进度；用户主动展开时查看成员、任务、依赖和获准结果，保留现有 Owner 审计视图。

### 2.3 用户补充与接管

- 用户在任务进行中补充“重点看移动端”时，绑定当前活动根任务，以版本化指令更新影响后续步骤；不另开一个并行任务重复执行。
- 只有后续计划需要重做的已完成部分才重新执行，说明原因与新增消耗；不能静默抹除旧结果。
- “暂停”停止新派发，已发出的调用按可取消能力收敛；“停止”撤销执行权并保留已产生费用和副作用事实。
- 同一房间存在多项活动工作时，将补充对象显示在输入区；仅在无法确定对象时询问用户。
- 用户可以接管或修改分工，但不必靠接管才能推进正常任务。

### 2.4 仅必要时出现的决策卡

```text
需要你的决定
报告已完成，但客户收件人尚未明确，需要确认本次发送目标。
收件人：……  附件：报告 v3  预计新增费用：……

[批准这次发送]  [仅保留草稿]  [取消]
```

决策必须对应已准备好的具体动作。一次答复只解决对应阻塞，不签发无限权限；同一阻塞不能反复询问。内部工作在授权内继续，不要求用户逐步查看报告、确认收到、批准汇总或发布进度。

### 2.5 完成态

主 Agent 返回最终结论、实际产物、重要验证与未解决问题。任务卡可展开协作与费用明细。自动完成条件与人工业务验收分别记录：系统可以证明步骤完成、测试或规则检查通过，不能伪称用户已验收质量。

## 4. 任务授权与信息流

### 4.1 一次任务授权的内容

由服务端根据用户请求、输入区可见设置与房间默认策略冻结，而不是由模型填写 authority 字段：

| 授权字段 | 含义 |
|---|---|
| 责任人与可委派成员 | 用户指定或默认主 Agent；仅本房间已启用、兼容且有权参与的成员 |
| 输入范围 | 本轮文字、上传材料及用户明确引用的版本；不自动扩大到其他房间或私密历史 |
| 阅读与回传规则 | 谁能处理哪些内容，子结果回给谁；不能把“在同一房间”当作私密内容读取权限 |
| 输出范围 | 返回给用户、允许的任务内共享、经批准的结构化公告；公开范围与外部发送另行判定 |
| 工具与副作用 | 房间、角色、任务、步骤和驱动权限的交集；账号凭据继续由服务端代管 |
| 预算与时限 | 根任务总量、并发、派发/深度上限、单次时限与未知用量处理 |
| 需用户决策的动作 | 超出既定范围或缺少明确授权的发送、部署等；已有明确授权且策略允许的动作不重复确认 |
| 有效期与版本 | 根任务、版本、撤销和停止代际；所有派生工作继承且不得扩大 |

普通请求默认允许任务团队在上述范围内协作；用户显式指定“只给 A”的材料继续只给 A，不能因为开启自主模式而自动授权给 B。必要时返回给有权阅读的用户，或一次说明确切缺口。

### 4.2 让内部协作自动发生

1. Agent 提交目标、候选执行者、依赖、所需输入与交付条件。
2. Runtime 核对成员、输入来源、预算和动作权限，原子创建子责任、执行 Scope 与派发记录。
3. 执行者只得到自身获准输入，结果按任务规则保存；调度恢复可只接收机器状态。
4. 需要正文的后继由服务端在有权范围内创建新的内容 Scope，输入账本自动衔接。
5. 汇总结果直接返回有权阅读的用户。多个内部阶段不要求用户重复授权相同已允许的数据流。

同一个 Agent 可以承担主协调与内容处理，但两类调用保持独立 Scope、原生会话和来源记录。读取私密正文后的自由文本计划、理由和摘要不能被塞进干净调度上下文；下一步根据获准状态、预设流程或合法内容范围执行。

### 4.3 自动发布的三类情况

| 情况 | 默认处理 |
|---|---|
| 结果返回有权阅读的用户，或在原合法范围内共享 | 自动，无逐条确认 |
| 根任务已包含受支持的结构化披露规则，例如完成状态、投票计数、按规则算出的阶段公告 | Runtime 验证来源与规则并自动发布，留下发布记录 |
| 受限原文/受限推理需要扩大接收范围，且没有相应任务授权；或外部发送缺少明确授权/确定目标 | 准备具体内容与目标，合并为必要决策；已有相应任务授权时直接执行，不伪造用户批准 |

模型能读内容，不等于它能签发新的披露权限。结构化规则不等于让模型生成一段 JSON 后自动当作安全内容。公开输出必须由已授权来源及服务端可校验的转换得到，或有覆盖该动作的明确授权。敏感词过滤、模型自报不涉密和另一模型审阅不能替代权限依据。

**自由自然语言、严格互相保密、用户零确认三项不能靠当前机制同时保证。** 首次产品交付承诺：普通授权内协作自动完成；秘密场景先以可校验的结构化流程实现零中途操作。任意自由讨论的自动披露需要另行明确授权语义，不能在本方案里暗中放宽为所有私密内容均可公开。

## 5. Runtime 与 Agent 工具设计

### 5.1 单一根任务

一个用户需求对应一个根 Run，界面中的“协作任务”是该 Run 的产品视图。内部阶段、委派、复核和汇总使用子 Subject/Attempt；不为每一步创建用户可见的新任务。

优先在同一根 Run 内完成，避免沿用手动汇总时创建独立新 Run、预算重复增加的行为。确有跨 Run 后继时，必须记录根关联并继承总预算；同一调用只记一次。现有 Supervisor Task 实体继续保留自身含义，不混作本次根任务主键。

新增能力使用独立的版本化契约，拟为 `features.autonomousCollaboration.version=1` 和 Tool API/Control Action v4。名称与兼容映射在 AC1 冻结；不重解释现有 v2/v3 动作。角色不因升级获得新的账户、工具或可读历史。

### 5.2 拟议动作

| Agent 动作 | 用途 | Runtime 约束 |
|---|---|---|
| `agent.delegate` | 向一位或多位成员提出各自不同的任务 | 检查任务内成员、输入来源、循环/依赖、交付要求、授权和预算 |
| `agent.aggregate` | 请求有权成员处理已完成结果并生成交付 | 自动建立内容 Scope；只注入获准来源，共用根预算 |
| `agent.emit` | 提交阶段更新或最终输出候选 | 自动裁定允许范围、结构化投影或必要审批；Agent 不能签发 Grant |
| `agent.request_user` | 请求缺失业务信息或必要决策 | 绑定真实阻塞，合并问题、去重，不能用于例行“是否继续” |
| `agent.complete` | 提交交付并结束当前责任 | 核验子义务、有效证据、工具状态与未知调用，不能仅凭口头“完成” |

工具参数为领域任务信息和服务端返回的受控引用。Run、Scope、Attempt、代际、预算授权、Policy/Grant 的 authority 来自执行绑定，不由模型传入。

委派动作成功后，Runtime 持久等待实际子工作；子任务完成时唯一唤醒父责任，无需 Agent 轮询或反复发计时等待。自动调整计划也产生版本化命令，不能篡改已完成结果或恢复旧权限。

### 5.3 原子性与恢复

- 创建子工作、继承授权、义务和命令回执在同一事务提交；重复动作返回同一事实。
- 运行图检查循环、自委派和无效依赖；有界重试、最大派发与总时限避免无限自我协作。
- 所有摘要、工具结果、附件、错误、流式输出和 SDK 会话遵守来源范围；不能从日志或进度旁路泄露。
- 暂停、停止、撤销后重新验证代际；迟到结果不能完成或触发后继。
- 只读失败在策略允许时重试或换用兼容成员；写入与外部操作先核对回执，不自动重放未知副作用。
- 未知用量继续占额，不能通过创建新子任务、换模型或新 Run 绕过。
- 等待状态必须有有效子义务、注册事件或用户问题，并显示对象和截止条件；主机长暂停后重新核验执行事实。

### 5.4 数据与边界

复用现有根 Run、Subject/Custody、Action Command、输入账本、工具回执及发布事实。新迁移只追加自主任务策略、计划修订与策略执行关联；具体表结构在 AC1 根据现有权威表冻结，避免同一状态双写。

策略版本、来源、执行代际与授权派生应能被审计。给 Agent 的能力句柄不能调用管理端 Owner HTTP 接口。迁移在当前 v17 之后追加，实际编号以实施时最新清单为准；既有迁移不修改。

## 6. 普通任务与狼人杀的目标流程

### 6.1 方案评审与文件交付

用户一次提交：“检查这份设计，分别评估实现与测试风险，合并意见并更新报告。”

主 Agent 选成员 → 分配不同材料 → 自动收集 → 对分歧追加一次核对 → 汇总并修改受控文件 → 验证实际文件版本 → 返回结论与文件。整个流程不要求用户填独立材料或点击汇总授权。新增审阅仍受根预算与合法来源约束。

### 6.2 狼人杀观察者模式

用户一次提交：“组织一场五人狼人杀，我只当观众。”

系统匹配受支持的流程说明，采用明确的五人简化规则：1 狼人、1 预言家、3 村民，先声明同票规则和胜负条件。主 Agent 选择可用玩家，不让用户逐一编写身份材料。可用成员不足、账户不可用时一次说明；首版使用现有启用成员，不自动新建永久角色或复制账户。

完整链路：

```text
自然语言请求
  → 确定规则、主持和玩家
  → 平台抽取身份并分别创建私密输入
  → 第一夜独立行动与查验
  → 规则裁决、自动公告
  → 白天结构化发言
  → 投票、计票、放逐与胜负检查
  → 必要时第二夜
  → 终局公告与完整回放
```

身份使用平台生成的独立数据项，授权绑定玩家，不能让一个读过全部身份的模型自行声称拆分后的文字互不泄密。预言家结果仅进入其后续获准输入；公开公告由已声明规则计算，终局按规则公开身份。

结构化声明支持玩家自称、建议对象与信心；声称是游戏行为，不能误当成真实身份。首版不承诺任意自由发言自动脱密。用户全程无需手动发牌、搬运材料、统计票数或批准每轮公告。

游戏只是通用任务系统的验收样例：使用可版本化、服务端校验的流程定义与转换组件。不得在 `scheduler.ts` 写死“检测到狼人杀关键词就按四步推进”，也不能用脚本预填玩家行动伪装成多 Agent 协作。

### 6.3 回归场景不能局限于游戏

至少同时覆盖：不同材料独立评审后汇总、代码/报告修改与独立复核、用户中途补充、一个成员失败后的有界调整、明确私密材料的受限流转、停止/重启与未知用量恢复。

## 7. 实施阶段与交付门槛

所有阶段状态均为待实施。建议顺序 **AC1 → AC2 → AC3 → AC4 → AC5 → AC6**；后续阶段可以并行准备界面与测试，但不得在能力未实现时对用户宣称默认自主协作可用。

| 阶段 | 实施内容 | 完成门槛 |
|---|---|---|
| AC1：任务契约与授权 | 冻结根任务、参与者、权限派生、共享预算、新版本协议及兼容策略；追加必要迁移 | 新旧契约互不误解；权限不能由模型扩大；子任务不新增总预算；旧任务/账本逐行保留 |
| AC2：Agent 动态委派 | 新工具、运行图、独立输入、不同成员不同任务、依赖唤醒、运行中调整 | 从实际 Agent 工具调用完成 A/B 独立工作及下一步；不预制批次；循环和重复命令被阻断 |
| AC3：自动收集与交付 | 任务内自动读取、私密汇总、合法结果返回、结构化输出规则和必要决策 | 内部委派到最终答复无逐条用户操作；越界只出现一次具体决策；无管理身份冒用 |
| AC4：默认单入口 | 普通发送接入新契约，任务卡、过程折叠、补充、暂停停止；旧表单移到高级入口 | 普通用户完成工作不进入材料表单；补充不重复开任务；桌面与 390px 可用；旧 Run 可继续查看/排空 |
| AC5：多轮流程与验收样例 | 可校验流程定义、阶段状态、平台裁决与自动公告；完整狼人杀及非游戏任务 | 用户一次请求后到终局，真实独立行动、合法公告和回放齐全；普通评审/文件任务同样自动完成 |
| AC6：真实组合与上线 | 模型 API/托管 Claude SDK 组合实测，完整故障/权限矩阵，房间灰度、回退和文档 | 每个开放组合有独立证据；失败与 unknown 不清除；用户参与指标达标；旧服务兼容和备份验证通过 |

Codex 真实角色验证继续按用户现有要求暂缓；不因此自动开启 Codex 新能力。账户连接测试、传输成功和模型口头叙述都不能替代端到端自主任务证据。

AC1–AC3 先用模型 API 与本机协议夹具建立闭环，再补托管 SDK。开发期新契约放在独立开关之后，产品默认入口切换需满足 AC4–AC6 的相应上线门槛；完整旧任务回归作为每阶段必要检查，不自动重跑历史失败游戏。

## 8. 验收标准

### 8.1 用户参与度

| 场景 | 预期用户动作 |
|---|---|
| 信息充分的普通分析/评审 | 一次发送，零次流程确认 |
| 授权内文件修改与复核 | 一次发送，零次搬运材料或逐步批准 |
| 受支持规则下的五人狼人杀 | 一次发送，零次中途场控，完成到胜负与回放 |
| 必要业务信息缺失 | 一次合并问题，答复后自动继续 |
| 超出权限/预算或未获授权的对外动作 | 对具体动作一次决策，不重复问“是否继续” |
| 用户停止/补充需求 | 一次操作或消息，持久化事实正确，不重复执行 |

“零次流程确认”建立在任务已具有所需权限、账户和额度的前提下；不能把需要的配置准备或异常权限伪装成自动完成。

### 8.2 工程与真实验收

- 必须从普通输入 HTTP/UI 路径创建新契约；不直接插入计划或替换冻结角色来宣称产品通过。
- 模型产生实际分工与控制调用；服务端只做范围、图、预算和结构化规则校验，不能替模型伪造业务结果。
- 跨步骤独立材料、同角色多 Scope、私密→公开切换、SDK 冷会话均有负向来源检查。
- 结果与来源变化、撤销、同一动作竞争、响应丢失、跨进程恢复均不导致重复委派、完成或发布。
- 机器完成与用户验收状态分开，实际文件/测试/规则证据与声明匹配。
- 子任务、汇总与修订累计受根预算限制；未知占额与外部效果在重启、换人、后继中保持。
- 正式记录输入/输出、真实供应商请求或未知内部请求、调用状态、证据目录和源业务库不变核对。
- 先保留既有完整矩阵，再新增自主工具、正常入口、连续阶段、用户参与次数和多后端验收；只增加与新风险对应的有效测试。

## 9. 灰度、兼容与回退

- 使用独立 `autonomousCollaboration` 能力声明与服务端准入开关；closed/preview/execute 语义与已有入口保持一致。
- 旧 v2/v3、固定材料任务、手工发布及 R7 人工验收 Run 不升级。当前 Owner 批准不能被改写为 Agent 批准。
- 新任务的人工/自动验收策略显式冻结；“把门禁藏起来”不能解除旧 Owner 阶段门禁。
- 灰度以房间为单位。关闭新准入后仍用兼容 worker 排空已有自主任务，不删除授权/动作/预算事实。
- 未识别新契约的 worker 在读写或调度前拒绝；数据库迁移追加后，回退须按匹配源码和一致性备份进行。
- 本方案不自动提交、推送、部署或关闭 Issue；这些操作按后续明确执行要求处理。
