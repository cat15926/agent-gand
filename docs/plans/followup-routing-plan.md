# 聊天室追问路由与任务级编排方案

状态：**已批准**
更新时间：2026-09-19
关联：[通用协作规划器与 Coordination Plan 设计](./coordination-planner-design.md) §13.4（任务级选择）
触发事件：真机会话 `31ec5657` —— 辩论结束后用户回复 Reviewer 裁决追问「介绍一下Claude的发展史」，系统重跑整条 pipeline（coder 抢答、coder-jitui 超时导致 run failed）。根因：回复定向信息丢失 + 无 plan 的追问无条件落入 pipeline 全量重跑，§13.4 的"简单追问快速路径"从未实现。

## 1. 设计原则

1. **编排属于任务，不属于房间**：辩论是 turn N 的任务，追问是 turn N+1 的新任务，复杂度独立判断。房间模式只是上一任务留下的偏好，不是每次追问的默认动作。
2. **误判成本不对称 → 默认偏轻**：复杂任务被单 Agent 简答，用户看一眼即可 `@` 升级，损失一次廉价回答；简单问题被拉起编排，用户白等数分钟并烧一轮 token。只有明确信号才走重编排（与方案 §7.4 置信度哲学同构）。
3. **显式意图最高优先**：定向（回复/`@`）与协议指令（"再辩论一轮""分别分析后汇总"）永远直接生效。
4. **判定器可升级**：MVP 用确定性选择器（阶段 B `chooseProtocols`，零成本）；阶段 D 落地后升级为模型规划（TaskBrief + 平台置信度），路由行为不变、判断更准。

## 2. Follow-up Router 决策表

拦截位置：dispatcher 对"无 coordination plan 的新 run"派发编排之前（collaboration 分支保持既有语义，不受影响）。

| 追问形态 | 判定来源 | 路由 |
|---|---|---|
| **结构化诉求**（文本含 分别/汇总/辩论/审查… 协议关键词） | 确定性选择器 | **最高优先**：重编排。协调房间（有 plan 历史）→ 服务端重新规划编译新 Plan 执行；其他房间 → 按房间既有模式编排（定向成员重排在前）。`@` 提及转为 recipientHint 供角色参考 |
| 回复某 Agent 消息、`@` 单人（无结构化诉求） | 显式（recipientIds 或 replyTo 推导） | 该 Agent 单独回应（快速路径），不编排 |
| `@` 多人（≤3，无结构化诉求） | 显式 | 并行征询这几位（快速路径多目标并行） |
| 无定向，选择器判**简单**（一般对话/开放交流） | Layer 1 | 快速路径：本房间**最近成功回复者**；无历史 → 首位具备 execute 能力的成员 |
| 无定向，选择器**模糊** | MVP 简化 | 按简单处理（默认偏轻）；推荐卡在阶段 2 提供 |
| 用户主动升级 | 逃生口 | `@` 多人即时生效；输入框"全队处理"开关（阶段 3 可选） |

> 决策顺序为 **结构化 > 定向 > 简单**（2026-09-19 真机会话 31ec5657 seq30 修正：`@A @B 分别调研，最后由 @C 汇总`是定向+结构化复合诉求，定向不得短路掉编排——否则汇总者永远不会被调度）。配套：归一化器只在"成员词+审查/裁决动词"同现时才设 `reviewAfterCompletion` 硬约束（"由 reviewer 汇总"是点名聚合而非终审）；`compileParallel` 支持"成员名邻近汇总词"的点名聚合者绑定。

## 3. 关键语义

- **最近成功回复者**：本聊天室内最后一条 `kind=agent` 且所属 run 状态为 `completed` 的发送者。
- **replyTo 推导**：`recipientIds` 为空但带 `replyTo` 且被回复消息来自 Agent → 视为对该 Agent 定向（服务端推导，覆盖 API 调用方；前端同时在所有模式下发送 `recipientIds`）。
- **追问引用历史产物**：快速路径 prompt 注入 `conversationHistory`（dispatcher 既有逻辑）+ 房间稳定工作区（`room-*`）跨 run 可见，"把刚才的裁决翻译成英文"类追问天然可用。
- **结构化追问的重新规划**：复用 `previewCoordination` + `compileCoordinationPlan`（校验通过且 decision=auto_start 才激活）；失败或低置信 → 落回快速路径（默认偏轻）。
- **观测**：快速 turn 的 span 记 `fastpath:directed|simple` 与目标 Agent；RunGraph 可区分单 turn 追问与编排 turn。
- **失败隔离**：快速路径单 turn 失败只影响该 turn（真机 stage-2 超时拖垮整个 run 的问题在快速路径下不存在）。

## 4. 实施阶段

- **阶段 1（MVP，2026-09-19 实施）**：显式定向 + 确定性简单/结构化判定 + 最近回复者快速路径 + 协调房间结构化追问重新规划。
- **阶段 2**：协议与房间模式不匹配时的**推荐卡**（复用创建时计划卡 UX，一键开始/切换，不静默换模式）；模糊态推荐卡。
- **阶段 3（随阶段 D）**：判定器升级为模型规划（TaskBrief + 平台置信度）；"全队处理"开关。

## 5. 验收标准

- 回复 Reviewer 裁决追问 → 仅 Reviewer 回应，run 单 turn 完成，不重跑 pipeline。
- `@` 多人追问 → 仅被点名的 Agent（并行）回应。
- 无定向简单追问 → 最近成功回复者回应；房间无历史 → 按 execute 能力选首位。
- 结构化追问（"再进行1轮辩论…"）在协调房间 → 生成新 Coordination Plan 并按协议执行，而非 pipeline 顺序重跑。
- pipeline/supervisor 房间的结构化追问 → 按房间模式编排（不静默切换协议）。
- collaboration 房间行为不变（其语义本就是本方案的子集）。
