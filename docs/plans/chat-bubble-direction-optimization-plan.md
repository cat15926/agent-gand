# 聊天气泡方向二次优化方案

状态：评审通过；已于 2026-09-14 实施并通过类型检查与前端生产构建。

日期：2026-09-14。针对当前多 Agent 聊天室中“用户与 Agent 消息方向相同”的体验问题重新设计。

实施结果：用户消息根据 `message.from === 'user'` 固定右对齐，头像位于右侧；Agent 与流式输出固定左对齐；系统、工具和轮次信息保持居中。已加入 90 秒连续消息视觉分组、引用强制断组、审查宽卡以及 420/768/1280px 响应式宽度规则。消息数据、调度和审计协议未改变。

## 1. 问题判断

用户反馈成立。当前 `MessageItem` 虽然通过紫色背景区分用户消息，但用户和 Agent 都使用相同结构：头像在左、内容从左向右展开、整行左对齐。用户需要先阅读名称或颜色才能确认消息属于谁，缺少常见聊天产品中“自己在右、对方在左”的直接空间认知。

当前方案文档的“用户和 Agent 均采用头像＋身份头＋正文的群聊行式布局”也不符合本次反馈，应被本方案替代。

本轮设计目标：

- 用户无需阅读名称，就能立即分辨自己的消息和团队消息。
- 保留多 Agent 群聊感，能快速识别 Planner、Coder、Reviewer 分别在说什么。
- 审查卡、代码块和长报告仍有足够宽度，不被普通聊天气泡的窄宽度破坏。
- 消息方向只由真实身份决定，不受 `to`、消息类型或主题色影响。

## 2. 推荐方向规则

| 消息来源 | 位置 | 头像 | 气泡 | 辅助信息 |
| --- | --- | --- | --- | --- |
| 当前用户 | 右侧 | 气泡右侧，可在连续消息中隐藏 | 紫色实底或强调底色，右下角较小圆角 | 接收人、时间、发送状态靠右 |
| Agent | 左侧 | 气泡左侧，使用 Agent 主题色 | 中性深色，左下角较小圆角 | Agent 名称、角色、接收人、时间靠左 |
| Reviewer 审查 | 左侧 | Reviewer 头像 | 左侧宽卡片；PASS 绿色边框，FAIL 红色边框 | 问题、文件位置和建议保持展开能力 |
| Agent 流式输出 | 左侧 | 对应 Agent 头像并脉冲 | 虚线气泡，原位增量更新 | 显示“Coder 正在回复” |
| 系统/工具/轮次 | 居中 | 无 | 细分隔条或紧凑状态胶囊 | 不参与左右对话方向 |
| 审批/阻塞 | 居中或内容区全宽 | 无个人头像 | 行动卡 | 明确操作按钮和影响范围 |

方向判定使用 `message.from === 'user'`，不能只判断 `message.kind === 'user'`。这样可避免未来导入记录、系统代理用户或消息类型扩展时产生方向错误。

## 4. 用户消息设计

用户消息采用右对齐容器：`flex-row-reverse` 或 `justify-end`，头像位于最右侧，气泡位于头像左侧。正文仍保持左对齐，避免中文长段落、列表和代码右对齐后难以阅读。

建议尺寸：

- 普通用户消息最大宽度为消息区的 68%，最大像素宽度 680px。
- 移动端最大宽度 84%，小于 420px 时隐藏“你”的头像以节省空间。
- 短消息宽度随内容收缩；长消息在最大宽度内换行。
- 用户气泡使用 `bg-violet-500/25`、轻微边框和 `rounded-2xl rounded-br-md`。
- 名称可省略或显示“你”；接收人、时间放在气泡上方并右对齐。
- 发送状态放在气泡右下方：发送中、已排队、处理中、已回应、失败。失败使用红色文字并提供重试，不只靠图标。

用户引用 Agent 消息时，引用块放在右侧气泡内部顶部，保持文本左对齐；使用被引用 Agent 的主题色作为左边框。点击引用仍定位原消息。

用户消息包含代码、表格或超过 12 行时，可放宽至消息区的 82%。不能为了保持气泡窄度压缩代码；横向滚动仅出现在代码和表格内部。

## 5. Agent 消息设计

所有 Agent 消息保持左对齐，因为它们共同属于“对方团队”。Agent 不按不同方向分散到左右两侧，否则三名 Agent 并行时会误导用户认为存在多个“自己”。

多 Agent 身份通过以下元素表达：

- 左侧主题色头像，显示名称首字或配置头像。
- 气泡上方固定显示 `Agent 名称 · 角色 → 接收人`。
- 普通正文使用中性背景，避免三种大面积主题色产生视觉噪声。
- Agent 主题色只用于头像、名称、左侧细边和状态点。
- Coder、Reviewer 连续交谈时仍全部左对齐，通过接收人和引用关系表达对话方向。

审查、最终结果和长报告属于富内容消息，最大宽度可达消息区的 82% 或 840px。普通 Agent 发言最大宽度 72% 或 720px。这样用户气泡具有聊天感，工程信息仍可读。

## 6. 连续消息合并

同一发送者在 90 秒内连续发送、且消息类型与 taskId 相同、没有轮次分隔时，合并为一组：

- 第一条显示头像、名称、角色和接收人。
- 中间消息缩小上下间距，不重复头像。
- 最后一条显示时间和处理状态。
- 引用回复、审查结论、任务切换或系统事件强制开始新组。

用户连续消息在右侧合并，Agent 连续消息在左侧合并。合并只改变视觉，不修改消息数据和审计顺序。

## 7. 系统状态与轮次

以下信息不应伪装成任何一方的聊天气泡：

- 第 N 轮开始、完成或失败。
- Coder 正在实现、Reviewer 正在审查。
- 工具调用完成、消息已排队、等待审批。
- 网络重连和恢复结果。

它们使用居中的分隔条、状态胶囊或行动卡。普通状态应紧凑；失败、审批和需要用户操作的状态默认展开。

## 8. 响应式规则

| 宽度 | 用户气泡 | Agent 气泡 | 头像与元数据 |
| --- | --- | --- | --- |
| ≥1280px | 最大 68% / 680px | 普通 72%，富内容 82% | 全部显示 |
| 768–1279px | 最大 76% | 最大 80% | 保留头像，简化角色说明 |
| <768px | 最大 84% | 最大 88% | 用户头像可隐藏；Agent 头像保留 |
| <420px | 最大 90% | 最大 92% | 时间和状态移至气泡下方，任务标签可折叠 |

左右对齐不能通过绝对定位实现，避免窄屏和长内容发生重叠。容器使用 flex，气泡使用 `min-w-0`、`overflow-wrap:anywhere`，代码块单独控制 overflow。

## 9. 具体实现方案

仅需调整展示层，无需修改数据库、API、调度器或消息协议。

建议把当前 `MessageItem` 拆成：

```text
MessageItem
├── UserMessageRow        右对齐、用户发送状态
├── AgentMessageRow       左对齐、Agent 身份与接收人
├── ReviewMessageCard     左侧富内容审查卡
└── SystemTimelineItem    居中状态
```

实现步骤：

1. 用 `message.from === 'user'` 计算 `isCurrentUser`。
2. 外层行根据身份切换 `justify-end` / `justify-start`。
3. 用户行使用 `flex-row-reverse`，Agent 行保持默认方向。
4. 将当前覆盖整行的用户紫色背景移到气泡本身，消息区背景保持统一。
5. 将身份头、引用块、正文、ReviewIssues 和状态组合进受控宽度的内容列。
6. 用户元数据使用 `justify-end`，正文继续 `text-left`。
7. StreamingItem 保持左侧，仅显示真实 Agent；协议流继续隐藏。
8. 加入相邻消息分组函数，不改变原始数组与序号。
9. 保留键盘、@、引用、智能滚动和任务关联行为。

预期主要改动文件：

- `apps/web/src/components/views/RunView.tsx`
- 可选新增 `apps/web/src/components/chat/UserMessageRow.tsx`
- 可选新增 `apps/web/src/components/chat/AgentMessageRow.tsx`
- `apps/web/src/styles.css`（仅补充无法用工具类清晰表达的长内容规则）

## 10. 预期效果

优化后用户进入聊天室时，能在约一秒内通过空间位置识别自己的发言；Agent 侧形成稳定的“团队区域”，多 Agent 身份不会混淆。用户发言、Agent 协作、系统进度形成右、左、中三条视觉轨道：

```text
右侧：用户意图与补充
左侧：Agent 发言、交接、审查与结果
中间：轮次、执行、工具与审批状态
```

相比当前版本，预计改善：

- “哪条是我发的”不再依赖阅读名称和颜色。
- 用户与 Agent 的对话关系更接近微信、Slack、Teams 等常见聊天心智。
- Coder 与 Reviewer 的内部协作仍集中在左侧，保留多人聊天室感。
- 审查问题和工程输出拥有独立宽度，不因右左气泡规则降低可读性。
- 系统过程与真人式发言分离，页面更像聊天，而不是执行日志。

## 11. 验收标准

1. 用户消息全部右对齐，头像位于右侧；Agent 消息全部左对齐，头像位于左侧。
2. 系统、工具、轮次和执行状态全部居中，不进入左右气泡轨道。
3. 用户正文保持左对齐，Markdown 列表、代码和表格可正常阅读。
4. Planner、Coder、Reviewer 之间的发言能通过头像、名称、接收人和引用区分。
5. Reviewer FAIL 卡左对齐，问题、路径、建议不截断；PASS 状态清晰。
6. 用户引用 Reviewer 后，右侧气泡内显示引用摘要，点击可定位原消息。
7. 发送状态与用户气泡同侧，失败可见且可重试。
8. 1440px、1024px、768px、390px 四档宽度没有重叠或页面级横向滚动。
9. 连续消息分组后不改变消息顺序、replyTo、taskId 和审计数据。
10. TypeScript 检查、前端生产构建和现有聊天室调度验证全部通过。

## 12. 评审建议

建议采用本方案的“右侧用户、左侧 Agent、居中系统状态”规则，并替换上一版文档中“用户和 Agent 使用相同群聊行式布局”的决定。

本轮属于纯前端展示优化，不改变已经实施的聊天室、多轮 Run、消息排队、Reviewer 返工和工作区逻辑。评审通过后可以作为一个独立变更实施和验收。
