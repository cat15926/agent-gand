## 2. 剩余内容与实施顺序

P0 表示扩展私密或写入能力前必须完成的正确性与安全基础；P1 表示诊断、治理、效率及验收闭环。R1 优先执行，以便先建立后续修复的故障证据。

| 阶段 | 优先级 | 工作类型 | 主要交付 | 前置依赖 |
|---|---|---|---|---|
| R1 故障因果与联合回归 | P1，首先执行 | 开发 + 补验收 | 跨分支失败关系、混合 Runtime 控制故障、真实 HTTP/WS 回归 | 现有基线 |
| R2 私密交互与文件权限 | P0 | 开发 | 用户私密消息入口、文件 ACL、逐成员上下文能力准入 | 可在 R1 后启动；文件归档与 R3 对接 |
| R3 完整产物与工作树快照 | P0 | 开发 | 仓库基线、受控改动、产物版本及可验证恢复 | R2 的权限契约；公开文件部分可先推进 |
| R4 私密及写入恢复 | P0 | 开发 | 私密/写入续跑与返工、副作用核对、隔离工作树承接 | R1、R2、R3 |
| R5 费用预算治理 | P1 | 开发 | 未知费用预留、费用限制、预算结转和后端能力声明 | 现有预算账本；与 R2–R4 可独立推进 |
| R6 多分支与精细返工 | P1 | 开发 | 跨引擎检查点、部分成员返工、验收清单版本化修订 | R1、R3；涉及私密/写入时还需 R4 |
| R7 调度效率优化 | P1 | 开发 | 差异化任务批量派发、并行汇合、确定性状态迁移 | R2、R5；复用 R6 的分支依赖规则 |
| R8 真实长链路验收 | P1，收尾门禁 | 补验收 | 经授权的真实混合后端、多阶段与故障恢复验收报告 | R1 通过；各场景对应功能完成 |

建议主线为 **R1 → R2 → R3 → R4 → R6 → R7 → R8**，R5 在 R1 后独立推进，并在 R7 前完成。R8 可先验收已有公开只读能力，新增场景随对应阶段交付补充，不能提前将未覆盖场景标为通过。

六类缺口的对应关系：私密协作 → R2/R4；写入恢复与归档 → R3/R4；恢复和返工扩展 → R6；费用预算 → R5；调度效率 → R7；完整诊断 → R1。剩余联合验收由 R1/R8 跟踪。

## 3. 分阶段实施内容与验收标准

### R1：故障因果与联合回归

状态：**本地实现与验收完成**（2026-10-11），[生效契约](../architecture/run-failure-diagnostics-v1.md)、[验收证据及边界](../reports/platform-collaboration-r1-acceptance-2026-10-11.md)。原始触发、依赖与后续取消按实际证据区分；同次调用及终态时已失败快照属于明确关联，不据此推断供应商故障或唯一终止原因。

**目标：** 能解释一个失败从哪里发生、影响了谁，以及为什么可以或不可以继续；先补齐已有功能的联合验收缺口。

实施内容：

1. 为诊断记录关联 Run、Dispatch/步骤、Attempt、执行、控制动作及来源事件，区分原始触发、依赖失败、后续取消、证据采集异常和未知结果。
2. 将多分支错误按因果关系展示，持久化必要的脱敏诊断及已有 request ID；无供应商证据时保留“无法确定”，不能把 SDK 等待推断为供应商故障。
3. 独立复跑 `verify:external-agents-c`。此前未完成的私密咨询、汇总、越权追问及控制中断检查现已通过，并补双向跨驱动交接后超时；夹具使用本机回环 MCP 与临时模拟进程。
4. 补真实本地 HTTP/WS 链路中的断连、重连、重复请求、提交前后重启、超时及晚到事件测试；与内存注入结果分别记录。

预期交互：任务卡显示原始失败和可执行的下一步；展开后看到失败成员、受影响事项、最近可信进度、有效时限及恢复阻断原因。

验收标准：中间成员超时不会被后续租约清理或取消覆盖；受控中断不会被当作已确认工具失败；断网/重启/重复确认不产生重复执行与重复副作用；私密内容不出现在未授权成员的诊断、消息和聚合中。联合夹具与网络测试均有独立通过记录。

主要落点：[执行诊断](../../apps/server/src/execution/errors.ts)、[执行记录](../../apps/server/src/execution/store.ts)、[公共恢复](../../apps/server/src/runtime/recovery.ts)、[任务卡](../../apps/web/src/components/TaskCard.tsx)、[Runtime C 夹具](../../scripts/verify-external-agents-c.mjs)。

### R2：私密交互与文件权限

状态：**本地实现与适用范围验收完成**（2026-10-11），[生效契约及能力矩阵](../architecture/private-interaction-artifact-acl-v1.md)、[验收证据](../reports/platform-collaboration-r2-acceptance-2026-10-11.md)。用户范围、受控附件、不可变文件版本、所有者授权审计，以及 Collaboration/Coordination 的适用隔离已交付。只读 CLI、旧共享上下文引擎和私密原生写入明确拒绝。受控版本归档及公开逐阶段检查点已由 R3 接入；跨 Run 私密/写入自动恢复及真实供应商验收分别留给 R4、R8。

**目标：** 用户能够直接创建受控私密事项，文本与文件拥有一致的信息边界，并按引擎实际能力准入。

实施内容：

1. 在聊天输入与任务预览中增加“公开 / 私密”及获准成员选择。公开定向指派仍保留公开语义；接收者与可见范围分别展示。
2. 文件产物绑定来源任务、阶段、版本、可见范围及授权成员。下载、读取工具、证据引用、索引检索、摘要和检查点恢复统一检查 ACL。
3. 将逐成员上下文与私密汇合规则扩展到其他适用编排引擎，建立能力矩阵；不具备隔离能力的工作流在预览阶段给出具体原因。
4. 校验私密追问、派生汇总和原生会话复用范围。扩大授权应有明确的所有者操作与审计，不能由 Agent 自动推断；历史公开消息不自动转为私密。

预期交互：用户发送前能看到“谁能看到”；私密消息显示范围标识，文件继承相应范围；无法执行的组合在预览中说明原因，不能静默切换编排方式。

验收标准：两名成员持有不同私密文本和文件，另一成员在消息、工具、证据、检索、摘要、会话复用和恢复上下文中均无法取得；公开任务与私密任务交替执行不会串用上下文。文件路径可知也不能绕过权限。

主要落点：[消息契约](../../packages/shared/src/message.ts)、[消息权限](../../apps/server/src/messaging/access.ts)、[上下文](../../apps/server/src/runtime/context.ts)、[执行证据](../../apps/server/src/execution/evidence.ts)、[聊天页面](../../apps/web/src/components/views/RunView.tsx)、[任务编辑](../../apps/web/src/components/TaskComposer.tsx)。

### R3：完整产物与工作树快照

状态：**本地实现与适用范围验收完成**（2026-10-11），[生效契约](../architecture/artifact-worktree-snapshots-v1.md)、[验收证据](../reports/platform-collaboration-r3-acceptance-2026-10-11.md)。追加迁移 v7 与阶段检查点 v2；全部声明产物、受控不可变版本、自包含 Git 基线及声明改动已接入 Owner 归档和隔离恢复。物理文件/文本单项 1 MiB，受控文件 256 KiB，完整载荷 16 MiB / 4000 文件，超限拒绝。私密字节保留加密，不落原生目录；私密/写入自动承接与跨引擎承接继续分别由 R4、R6 跟踪。

**目标：** 交付与恢复依赖可验证快照，覆盖声明的全部产物及必要工作树状态。

实施内容：

1. 将 R2 已有受控文件版本接入完整产物清单与检查点，覆盖全部声明产物；沿用来源、权限、哈希、大小、类型、阶段及验收版本，声明产物缺失时不能将归档标为完整。
2. 保存可恢复的 Git 基线和受控工作树变更，包括新增、修改、删除及受支持的二进制产物。限制、排除范围及不支持类型在预览中披露。
3. 恢复到新隔离工作树，核对基线、路径、链接、内容哈希、权限与快照版本；损坏、缺失或漂移阻断确认。
4. 定义归档保留、清理与引用规则，保留已验收和被后续任务引用的证据。账户凭据、原生登录目录及未声明的敏感文件不进入交付归档。

预期交互：交付面板可查看文件版本及变化；续跑预览展示保留产物、仓库基线、将恢复的改动和未包含内容。

验收标准：移除旧临时工作区后仍能重建声明的已确认产物；篡改、路径逃逸、链接替换及权限漂移被拒绝；恢复不会覆盖用户当前工作树或泄漏私密文件。

主要落点：[快照编译与恢复](../../apps/server/src/artifacts/snapshots.ts)、[自包含 Git 基线](../../apps/server/src/artifacts/snapshotGit.ts)、[检查点编译](../../apps/server/src/orchestration/businessCheckpoint.ts)、[检查点归档](../../apps/server/src/orchestration/businessCheckpointStore.ts)、[Owner 界面](../../apps/web/src/components/ArtifactSnapshotPanel.tsx)。

### R4：私密及写入恢复

**目标：** 在已有只读恢复契约上，扩展经过权限与副作用核对的私密和写入承接。

实施内容：

1. 公共恢复资格核对消息授权、进程收敛、工具账本、实际工作树及外部副作用，明确“确认完成、确认未执行、结果未知”。
2. 私密检查点按当前接收成员授权重建上下文和产物；账户、角色、权限或接收范围变化触发重新预览。无法合法迁移的事项明确阻断。
3. 写入续跑和返工使用 R3 的隔离快照，只执行核对后确定的剩余事项。未知写入副作用先核实或进入人工处理，不能默认重跑。
4. 延续原子确认、唯一后继、旧终态不可变、阶段账本封存和预算结转；重新核对新工作树中的交付证据。

预期交互：失败任务卡提供资格与预览入口，展示已确认改动、待执行步骤、私密范围及需核实事项；确认后建立关联任务，并可返回查看原失败记录。

验收标准：超时发生在写入前、写入后和提交响应丢失时均不会重复产生副作用；重复确认只生成一个后继；部分提交失败整体回滚；私密恢复不扩大授权；已确认步骤、旧验收及旧终态不被改写。

主要落点：[公共恢复](../../apps/server/src/runtime/recovery.ts)、[原生执行恢复](../../apps/server/src/execution/recovery.ts)、[工具账本](../../apps/server/src/tools/executions.ts)、[业务返工](../../apps/server/src/orchestration/businessRework.ts)。

### R5：费用预算治理

**目标：** 将已知、估算、预留和未知消耗统一纳入派发决策，并准确说明限制强度。

实施内容：

1. 增加 Run/阶段费用政策、币种与计价来源版本，区分供应商实测费用、可计算费用、估算/预留额度和未知费用；计价必须覆盖适用的输入、输出及其他收费项。
2. 在派发前原子预留额度，完成后按可信用量结算；缺失 usage、价格或超时结果保留未知状态及额度，不按零处理。
3. 续跑、返工和多分支统一结转预算，不能用新 Run、换成员或价格变更重置已用额度；并发派发不能重复消费额度。
4. 明确后端可落实的硬限制和估算控制。无法可靠约束费用上限的后端不承诺严格硬预算；严格模式应在预览准入时拒绝或停止新派发。

预期交互：执行设置选择费用限制及控制策略；预览说明可落实程度；预算面板分别展示已知、预留、未知和剩余额度，未知不会显示为免费。

验收标准：全部未知、部分未知、价格未知、并发预约及取消后仍可能收费的场景均有一致政策；预算耗尽阻断后续调用；连续续跑/返工不重置额度；SDK/Codex 的实际限制能力在预览与运行时一致。

主要落点：[执行预算](../../apps/server/src/orchestration/executionBudget.ts)、[执行记录](../../apps/server/src/execution/store.ts)、[共享执行契约](../../packages/shared/src/execution.ts)、[任务编辑](../../apps/web/src/components/TaskComposer.tsx)。

### R6：多分支与精细返工

**目标：** 保留正确分支，只重做受到影响的工作；将恢复资格一致接入各引擎的既有恢复入口。

实施内容：

1. 建立分支依赖与检查点兼容矩阵，分别接入 Collaboration、Coordination、Pipeline、Supervisor 的适用入口。不同引擎无需拥有相同恢复算法，但必须遵守共同授权、预算和副作用规则。
2. 支持选择部分成员返工，并计算必须一起重做的依赖项及汇合结果；无法证明独立时保留全阶段返工。
3. 验收清单或分工修改生成新契约版本，展示受影响的验收、产物和后续阶段；只继承仍满足新契约的结果，不能改写原标准或原验收决定。
4. 将公共恢复资格与既有步骤重试、分支重试及暂停恢复对接，统一说明能力和阻断原因，避免新增顶层协作模式。

预期交互：返工面板选择成员及修改内容后，预览显示“保留 / 必须重做 / 需要重新验收”；最终执行集合由依赖校验确定，不能任意跳过必要事项。

验收标准：并行分支中一个失败，独立成功分支不重复执行；被修改产物的下游验收失效并重新处理；重复或并发修订不会产生多个后继；不兼容检查点明确拒绝，不静默降级为全量重跑。

主要落点：[业务契约](../../apps/server/src/orchestration/businessContract.ts)、[阶段执行](../../apps/server/src/orchestration/businessStageExecution.ts)、[检查点](../../apps/server/src/orchestration/businessCheckpoint.ts)、[返工](../../apps/server/src/orchestration/businessRework.ts)、[共享业务类型](../../packages/shared/src/business.ts)。

### R7：调度效率优化

**目标：** 平台处理可确定的确认和状态迁移，将模型调用用于需要判断与表达的工作。

实施内容：

1. 在阶段契约中表达每名成员的独立目标、接收范围、依赖与汇合条件，支持受控的差异化批量任务，避免通过共享咨询泄漏不同成员的信息。
2. 无依赖的任务按并发上限和预算预约执行；汇合只使用获准的已确认结果，不能隐式拼接各成员私密全文。
3. 派发回执、状态更新和满足明确条件的阶段迁移由服务端持久化处理；保留模型分析、实质交付及用户验收，不能把确认回执当作完成。
4. 预览估计派发规模及预算，运行中显示实际模型调用、排队和汇合情况。会话复用继续检查账户、角色、工作区、权限和信息范围。

预期交互：沿用统一任务入口，在阶段分工中表达独立任务和依赖；预览说明哪些可并行、谁能看到结果以及何时等待验收。

验收标准：同一夹具任务减少仅用于确认的模型调用，有前后对照；并行不会超卖预算、越权汇合或跳过验收；取消和部分失败能稳定收敛；私密内容不会因批量派发和会话复用扩散。

主要落点：[阶段执行](../../apps/server/src/orchestration/businessStageExecution.ts)、[预算](../../apps/server/src/orchestration/executionBudget.ts)、[Runtime 上下文](../../apps/server/src/runtime/context.ts)、[任务编辑](../../apps/web/src/components/TaskComposer.tsx)。

### R8：真实长链路验收

**目标：** 在可控夹具通过后，用少量经授权的真实账户任务验证实际集成与长期协作。

实施内容：

1. 建立明确执行入口，记录获准账户/模型、任务范围、调用与时间上限、允许的写入范围及费用政策；隔离业务数据，报告不包含凭据。
2. 使用实际 Claude SDK、Codex app-server 与模型 API 覆盖公开只读阶段执行、拒绝返工、失败续跑及已验收结果继承。
3. 在 R2–R7 对应功能完成后，补私密信息、受控文件写入、多分支、网络中断和重启恢复；不能以账户登录或最小模型连接成功代替任务执行验收。
4. 记录正确性、调用规模、各阶段耗时、未知用量比例、预算执行、人工干预及恢复结果。受环境或账户条件影响未完成的项保持“未验证”。

预期交互：用户沿正常任务入口完成预览、执行、交付、拒绝/接受及续跑，并能核对保留结果和待办；桌面与手机均覆盖关键操作。

验收标准：真实网络与真实供应商任务均有可复核的 Run 和证据；已验收工作不重复执行；私密信息不越权；未知副作用不重放；用户提前结束、接受部分结果与原目标达成分别呈现。

1. 新数据结构使用追加迁移和显式契约版本；旧任务按原冻结契约解释，不自动补授权、重分类消息或修改验收。
