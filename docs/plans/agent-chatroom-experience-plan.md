# 多 Agent 聊天室体验优化方案

状态：评审通过；核心范围已于 2026-09-14 实施。

日期：2026-09-13，2026-09-14 更新实施状态。基于提交 `76cb4dc` 完成分析并实施。

已实现：聊天室与多轮 Run、稳定房间工作区、历史回填、消息序号与幂等发送、运行中排队、@ 接收人、引用回复、审查问题卡、轮次边界、结构化协议流隐藏、聊天室级审批过滤及集成验证。当前实现把每条用户续聊作为一个可审计的新 Run 串行执行；“只读讨论”独立通道、执行中断和附件仍属于后续增强。

界面方向修订：本文件原定用户与 Agent 使用相同方向的群聊行式布局。该决定已根据使用反馈废止，后续以 [聊天气泡方向二次优化方案](./chat-bubble-direction-optimization-plan.md) 的“用户右侧、Agent 左侧、系统状态居中”为准。

## 1. 建议与预期结果

将当前“运行消息查看器”升级为“用户与 Agent 团队共同参与的聊天室”。保留已有的任务调度、审查返工与审计能力，在主界面回答四件事：**谁在做什么、正在和谁沟通、发现了什么问题、接下来会发生什么**。

建议分两阶段实施：先让已有协作过程可读，再实现同一聊天室的连续交流。两个阶段共同构成完整体验，仅完成第一阶段不能宣称已经支持真正的群聊。

目标体验：

- 用户进入房间即可看到主管、Coder、Reviewer，以及各自当前工作状态。
- Planner 指派、Coder 提交、Reviewer 反馈、Coder 修复、Reviewer 复审在同一条可追踪对话中呈现。
- 用户直接回复某条审查意见，或 @ 某位 Agent 提问；输入不会悄悄创建一个无关会话。
- 问题位置、修改建议、执行轮次和验收结论直接可见，长代码和日志按需展开。
- 完成后仍可在原房间追问或提出新需求；每轮执行有独立边界、状态和记录。

本文基于源码分析，未做本轮浏览器实测或用户访谈；阅读效率提升属于预期目标，需按第 10 节验证。

## 2. 当前体验问题及代码依据

| 当前问题 | 实现依据 | 用户影响 | 优化方向 |
| --- | --- | --- | --- |
| 看起来是聊天，实际每次发送都启动新运行 | `apps/web/src/components/views/RunView.tsx` 的 `Launcher.launch()` 总是调用 `api.startRun()` | 无法自然追问、补充上下文 | 引入持久聊天室，明确区分发消息与新执行轮次 |
| @ 会改变团队构成 | Launcher 用提及列表替换 `effectiveAgents`，并剥离正文中的提及 | @coder 可能排除主管和 Reviewer，语义偏离群聊 | @ 仅表示收件人，不改变当前房间成员与审查规则 |
| Agent 间通信像各自的长报告 | `MessageBubble` 仅展示发件人和正文，不消费 `to/taskId/replyTo/messageType/payload` | 看不出谁回应谁、哪条意见推动了修复 | 消息头、引用、任务标签、语义卡片 |
| 已有审查结构没有充分展示 | `scheduler.ts` 写入 verdict/summary/issues；聊天气泡只渲染 body，任务栏仅显示审查摘要 | 问题位置与修改建议不直观 | 聊天流中的审查结果卡 |
| 回复链数据基础存在，但编排链没有填充引用 | shared Message 有 `replyTo`，当前 scheduler 发消息未提供它 | 返工前后难以对应 | 发送时记录确切被回复的 messageId |
| 所有流式输出追加在消息列表末尾 | `RunView` 将 `state.messages` 和 `state.streams` 分别渲染 | 并行输出与最终消息容易跳动、错位 | 稳定消息占位与原位更新 |
| 流式身份依赖解析 span 名称 | `StreamingBubble` 从父 span 的 `name` 推导 Agent | UI 与调试文本格式耦合 | 事件直接携带 agentId/taskId/attemptId/messageId |
| 审查原始 JSON 可能在生成过程中进入聊天 | reviewStep 要求模型输出 JSON，通用 delta 被 RunView 渲染 | 用户看到协议片段而非审查结论 | 协议流只显示“正在审查”，验证后渲染结果卡 |
| 输入能力弱 | 单行 input、Enter 直接 launch，仅有 finally 无可见失败处理 | 多行需求、中文输入、失败重发体验不足 | 多行输入、输入法保护、草稿和错误反馈 |
| 上下文面板占用固定宽度 | SessionSidebar 为 w-60、RightPanel 为 w-80，RunView 还处于全局导航内 | 主对话区被挤压 | 可收起侧栏、按需详情抽屉 |
| 系统提示统一折叠、审批与聊天脱离 | MessageBubble 对 system/tool 统一 details；RightPanel 审批集合未按当前 run 过滤 | 关键阻塞不突出，其他会话审批可能干扰当前判断 | 当前房间阻塞置顶，跨房间提醒单独标识 |
| 消息落库不等于 Agent 收到并行动 | `POST /api/messages` 调用 inbox.post；post 只写库和广播，buildWorkContext 不消费任意用户新消息 | 仅新增发送按钮会产生“假续聊” | 明确接收、排队、消费与调度语义 |
| 重连与消息合并存在稳定性风险 | store 的 message 事件直接 append，runDetail 整体替换明细 | 重复投递或快照与增量交错可能丢失/重复展示 | 唯一 ID 合并、服务端顺序及断线补齐 |

已有能力可复用：Markdown/GFM、Agent 名称与颜色、WS 增量、任务和执行记录、结构化 Review、失败重试、工作区与审批。不需要为“聊天感”额外制造 Agent 闲聊。

### 3.1 信息布局

- 左侧：聊天室列表，标题、最新一句摘要、更新时间、待处理徽标；执行轮次在房间内查看，不挤占会话列表。
- 顶部：房间标题、成员头像和角色、工作区、当前执行状态；“进行中”进一步说明谁在实现、谁在审查。多任务并发时显示数量，展开可见各任务。
- 中部：公共消息流。用户和 Agent 均采用头像＋身份头＋正文的群聊行式布局；用户消息用轻微底色区分，不依赖左右位置理解身份。
- 底部：多行输入框，@ 选择、回复引用、发送状态；团队/模式/工作区放在建房设置和房间信息中，不在每次发送时重复选择。
- 右侧：任务、产物、审批及诊断抽屉，默认收起；点击消息的任务/文件/问题即可打开对应详情。
- 低于 1200px 时优先收起右侧，低于 900px 时房间列表改抽屉，手机只保留一栏。宽表格和代码在自身区域横向滚动。

### 3.2 消息外观

每条消息固定包含：头像、名称、角色、接收人、时间、正文；按需追加任务、轮次、引用、发送状态。颜色辅助识别，状态必须同时有文字和图标。

建议正文 14–16px，辅助信息不低于 12px。普通消息最大内容宽度约 800px；长报告首屏显示摘要和展开入口，代码块提供复制、语言标签和展开。最终结论、阻塞和待用户决定项不可被普通折叠规则隐藏。

无任务关联的自由问答显示“讨论”；任务关联发言显示“登录接口 · 第 2 次实现”。头像表示角色身份，不将“Agent 已配置”误标为“在线”；活跃状态由真实执行记录推导。

## 4. 消息语义与直观输出

| 现有/新增类型 | 主流显示 | 详情/动作 |
| --- | --- | --- |
| assignment | 主管 → Coder：任务标题、验收摘要 | 查看任务与依赖 |
| review_request | Coder → Reviewer：提交摘要、实现轮次 | 查看完整输出与产物 |
| revision_request（Reviewer 发起） | Reviewer → Coder：需要修改、问题数量 | 问题位置、原因、建议、引用提交 |
| revision_request（主管发起） | 第 N 次修复已安排 | 关联审查；与上条反馈相邻时降为小状态行，避免两张重复大卡 |
| review_result | 审查通过 / 需关注，关联实现轮次 | 查看审查项；PASS 有 warning 时仍显示警告 |
| result | 任务结果；主管最终消息为本轮结论卡 | 已完成、失败、未验证、产物与后续建议 |
| handoff | A → B：交接摘要 | 关联任务与来源 |
| informational / 用户讨论 | 普通聊天行 | 回复、复制、@ |
| tool / 常规 system | “读取 3 个文件 / 执行 2 条命令”等过程摘要 | 展开原始日志、耗时与错误 |
| 阻塞 / 审批 / 失败 | 明确的行动卡，默认展开 | 审批、查看原因、允许时重试 |

展示层依据结构化数据生成固定文案，不额外调用模型伪造“收到”“正在思考”等发言。任务开始显示状态行即可；只有确实保存的 Agent 输出才以 Agent 发言呈现。若输出缺少摘要，以标注为“正文预览”的截断文本降级，不把截断内容冒充完整结论。

审查结论必须来自通过协议验证的 Review。JSON 生成或协议重试期间只展示审查状态；失败时展示“审查未完成”，不能展示 PASS。过程摘要、原始消息和 Trace 共用来源 ID，详情不重复生成聊天消息。

引用支持点击定位原消息；并行任务按 taskId 筛选为任务讨论串，顶部显示“正在查看任务讨论”，一键回到完整房间。第一版不引入复杂多层嵌套回复。

产物卡必须来自真实文件写入/产物登记，不从模型提到的路径推断文件已存在。预览复用工作区权限边界；外部工作区继续走现有审批。文件不可访问时保留路径和原因，不能提供失效的“查看成功”体验。

## 5. 完整对话示例与预期效果

以下内容是设计示例，不是当前运行结果：

1. **你 → 团队**：请实现登录接口，并检查空输入。
2. **Planner → Coder**：指派“登录接口”，验收包括空密码处理；完成后由 Reviewer 审查。
3. **Coder → Reviewer**：已提交第 1 次实现。〔输出〕〔关联产物〕
4. **Reviewer → Coder**：需要修改：空字符串未拦截。卡片列出 auth.ts:42、问题与修改建议，引用第 1 次提交。
5. **状态**：Coder 正在执行第 2 次实现。无需再生成一句假的“收到”。
6. **你回复第 4 条并 @Coder**：也请处理只含空格的密码。消息显示“已接收，等待下一执行边界”。
7. **状态回执**：补充要求已纳入“登录接口补充校验”任务。若第 2 次实现已开始，其上下文不被偷偷改写；补充在后续任务处理，并再次审查。
8. **Coder → Reviewer**：补充校验已实现。引用补充要求与相关提交，列出有证据的变更摘要。
9. **Reviewer → 团队**：审查通过。展示实际验证证据；未执行测试时明确写“测试未执行”。
10. **Planner → 你**：本轮完成，展示最终产物和验证情况。
11. **你 → Reviewer**：为什么要校验空格？在原房间得到解释，记录为讨论，不默认重跑全队或修改代码。

用户应能在主流中完成“理解问题—补充要求—看到处理状态—确认结果”，而不必打开 Trace 或理解 attempt 状态枚举。

## 6. 交互与调度规则

### 6.1 房间、执行与消息的关系

新增 Conversation（聊天室），一个房间包含多次 Run。Run 继续表示一次有明确目标和终态的执行，Task/Attempt/Review 仍属于对应 Run。房间保存成员、模式、工作区；已执行轮次的配置是不可变快照。第一版禁止运行中更换工作区，空闲时切换需明确说明下一轮使用的目录。

已有每次运行独立目录不能直接满足跨轮延续。新房间首次执行前建立受管的稳定工作区绑定，后续轮次显式复用；旧 run 的独立目录需通过后端解析并登记为受管引用，不能简单传空 workspace 导致新一轮换目录，也不能把任意路径伪装成已授权的外部工作区。

### 6.2 发送与接收

- 无 @：由主管接收并路由；流水线房间由协调层接收，保持既定 Agent 顺序。
- @ 单人：定向交流，团队成员不变；公开显示接收人，该消息不是私聊。
- @ 多人：每名接收者独立生成可追踪的回复工作项，受房间队列和并发限制；不自动向每名成员广播整段历史。
- 回复：保存 replyTo，默认继承 taskId 和接收方；用户可以显式更改接收方。引用必须属于当前房间。
- 发送状态分开表达“发送中 / 已接收 / 已排队 / 已纳入任务 / 已回应 / 处理失败”；服务端持久化成功只代表已接收。
- 新增“讨论 / 执行补充”轻量意图选项，可自动建议但必须显示实际路由。讨论默认只读工具；涉及写入的请求转为执行任务，不能因措辞模糊在讨论中直接修改工作区。
- 未知 @、无成员、已归档房间给出明确错误；发送失败保留草稿并可重试。

### 6.3 运行中的补充

第一版采用持久队列，在安全边界消费：Agent turn 完成后、下一任务领取前、最终汇总前。当前实现是 ready wave 调度，可先在每个 wave 前后检查队列；等待中的审批不应被新消息绕过，UI 告知补充仍在等待。

每条补充形成明确决策：纳入尚未执行任务、创建后续任务、仅回答问题或等待用户澄清。记录 consumedByTaskId/turnId 与原因。已开始的 Attempt 输入快照不修改；已完成任务的新要求创建后续任务，保留原审查证据。并发补充对同一任务的应用按服务器接收顺序串行化。

Run 收尾与新消息接收必须通过同一房间调度锁/事务决定：收尾前已接收的执行补充阻止提前发布“全部完成”；收尾后到达的补充在同房间创建新 Run。禁止消息落库后无人消费的间隙。

第一版不承诺立即中断正在执行的模型或 shell，也不提供没有实际取消能力的“停止”按钮。终止和抢占作为后续能力，需贯通 AbortSignal、工具进程、Attempt 与任务终态。

### 6.4 两种编排模式

| 场景 | 顺序流水线 | 主管委派 |
| --- | --- | --- |
| 群聊展示 | 如实显示 Agent 顺序发言与交接 | 显示任务指派、并行工作与审查往返 |
| @ 提问 | 同房间排队执行定向只读讨论 | 同房间排队执行定向只读讨论 |
| 执行中补充 | 第一版明确排入下一轮流水线，不改当前累计上下文 | 在安全边界接入现有或后续任务 |
| 审查失败 | 不把既有流水线虚构为自动返工；需要闭环时在下一轮显式选主管模式 | 复用当前 Reviewer → 修复 → 复审闭环 |
| 结束后追问 | 同房间保留历史，独立讨论或新执行轮次 | 同左 |

## 7. 技术实现设计

### 7.1 前端组件与状态

将 RunView 拆为 RoomHeader、RoomTimeline、ChatMessage、ReviewCard、ResultCard、ActivityGroup、ChatComposer、TaskThreadDrawer；复用 Markdown 和审批卡。SessionSidebar 升级为房间列表；RightPanel 转为按房间和轮次过滤的抽屉。

新增纯展示转换层 `toChatItem`：将现有 message、review、attempt 映射为统一消息视图，保留 sourceId。展示映射不写回任务状态。任务状态翻译为中文，错误信息保留原文详情。

store 使用 messageId 唯一合并；活动流按正式 messageId 原位更新。流结束与最终消息的到达顺序不能导致闪空；只有正式消息到达或明确失败才替换占位。结构化协议流不进入普通 Markdown 渲染。

滚动规则：在底部附近时跟随新消息；用户向上阅读时保持位置，显示“有 N 条新消息”；切换房间保存阅读位置。中文输入 composition 期间 Enter 不发送，Shift+Enter 换行，按钮与快捷键共用幂等发送逻辑。

### 7.2 数据与协议增量（拟定）

| 对象 | 新增关键字段或表 | 目的 |
| --- | --- | --- |
| conversations | id、title、members、mode、supervisorId、workspaceRef、createdAt、updatedAt、archivedAt | 保存聊天室和稳定工作区 |
| runs | conversationId | 同一房间多轮执行；保留现有 runId 引用 |
| conversation_messages | id、conversationId、runId 可空、sourceMessageId 可空、from/to、body、replyTo、taskId、seq、clientMessageId | 统一用户讨论与已有执行消息；sourceMessageId 唯一，避免双份可编辑事实 |
| conversation_inbox | messageId、recipientId、status、consumedByTaskId/turnId、lease、error | 可靠消费及状态回执；消息＋接收项同事务写入 |
| discussion_turns | id、conversationId、triggerMessageId、agentId、status、inputSnapshot、output | 非执行问答可追踪，不伪装成任务完成 |
| 流式事件 | conversationId、messageId、agentId、taskId、attemptId、displayKind、deltaSeq | 稳定归属、排序、重连去重 |
| 审查/产物引用 | reviewId、workAttemptId、artifactId | 将卡片关联至真实证据 |

原有 messages 仍是运行消息事实源，conversation_messages 中的 sourceMessageId 项作为只读投影；新增用户讨论由聊天室表作为事实源。先实现事务内投影，避免两个表各自改正文。后续如统一消息存储应单独迁移，不同时维护两套调度状态。

建议 API：

```text
POST /api/conversations                         创建房间并绑定工作区
GET  /api/conversations                         列表与未处理状态
GET  /api/conversations/:id/messages?afterSeq=   消息回补/分页
POST /api/conversations/:id/messages            接收并排队，不直接承诺执行完成
POST /api/conversations/:id/runs                创建房间内新执行轮次
GET  /api/conversations/:id/runs                历史轮次
```

消息请求包含 clientMessageId、body、recipientIds、replyTo、taskId、intent；from/kind 由服务端确定为当前用户，客户端不能伪装 Agent。收件人必须属于房间，taskId、引用和 runId 必须匹配房间。旧 POST /api/messages 保持兼容但不作为新 UI 的执行入口；需限制其身份字段，避免绕过新规则。

服务端分配房间内递增 seq；客户端按 seq 排列正式消息，按 ID 去重。消息创建与 inbox 入队同事务；事件先落库后广播，重连按游标补齐。补充调度采用租约和条件更新领取，崩溃恢复可重试；外部工具副作用不宣称天然 exactly-once，重试前检查既有 Attempt 与产物证据。

### 7.3 上下文与成本边界

contextBuilder 按“当前任务＋引用消息＋已接收的相关补充＋依赖结果＋相关审查＋房间摘要”构造输入。记录消费消息 ID 与输入快照，避免把所有日志重复送入模型。

房间摘要保留来源范围，重要约束保留原文引用；超出预算时提示需要拆分任务。Agent 不因看到别人的每条发言自动响应；只有工作项或明确 @ 触发回复，并设最大讨论跳数、每轮预算和失败上限，防止无限互相 @。

## 8. 实施阶段与交付边界

### 阶段 A：让现有协作过程可读（建议 3–5 个工程日）

1. 群聊消息布局、身份/接收人/任务/轮次，Review 与结果卡；状态与异常中文化。
2. scheduler 填充真实 replyTo、reviewId、attempt 引用，提供明确流式归属。
3. 稳定流式占位、智能滚动、详情抽屉、关键阻塞展示和审批范围修正。
4. 将现阶段输入明确标记“启动新任务”；仅在阶段 B 完成后改为可续聊的“发送”。

交付结果：能直观看到当前审查修复闭环；不承诺运行中插话被处理。

### 阶段 B：让聊天室可连续交流（建议 6–10 个工程日）

1. Conversation、稳定工作区、旧 run 回填、房间内轮次切换。
2. 多行输入、@/回复、草稿、发送幂等、房间消息与接收队列。
3. 定向只读讨论、主管模式安全边界补充、流水线下一轮补充。
4. 上下文构造、消费回执、收尾竞态处理、断线与崩溃恢复。
5. 全链路验收与旧 API/旧记录回归。

交付结果：用户可在同房间提问、补充、查看处理进度和继续下一轮，实现本文第 5 节完整场景。

### 后续增强（不纳入首轮承诺）

运行抢占与真正停止、并行分支讨论、附件上传、完整文件 diff 预览、复杂 Agent 自主协商与动态改计划。基础产物链接优先复用真实产物能力；不存在可验证产物来源时先保留输出摘要。

以上为单人熟悉代码情况下的粗估，需依据数据迁移与恢复测试结果调整；不是确定交付日期。建议按 A/B 两个可独立验收的里程碑实施。

## 9. 迁移与兼容

- 每条历史 Run 回填为一个独立聊天室，不自动按相似标题合并；旧消息、任务、审查 ID 保持不变。历史房间保留原先的独立 Run 工作区语义，后续轮次可读取聊天记录，但不会迁移旧文件；新建聊天室使用稳定房间工作区。
- 缺少 replyTo 的旧记录只显示“关联任务”，不推断成确定引用关系；缺少身份元数据的旧流采用兼容展示。
- 旧接口继续提供运行视图；新 UI 经功能开关切换。关闭开关仅回到旧展示，不能删除聊天室队列或让已接收补充消失；有待处理补充时保持后台消费或显式标记待恢复。
- 数据迁移先备份，验证历史数量、顺序、工作区可访问性和幂等回填；不通过则不切换新入口。
- 不把现有取消待执行任务扩展描述为“停止整个运行”。

## 10. 验收标准与验证方法

| 验收项 | 预期结果 | 验证方式 |
| --- | --- | --- |
| 协作可读 | 不打开 Trace 可识别指派、提交、FAIL、修复、PASS 的角色和关系 | 固定 mock 演示＋用户走查 |
| 审查直观 | blocking/warning、路径、建议和轮次可见，JSON 不进入普通流 | PASS/FAIL/非法 JSON 三类样本 |
| 真实续聊 | 连续发 3 条消息仍在同房间，@ 不删除成员 | API 与界面联调 |
| 执行补充 | 每条成功接收的补充有排队状态及最终消费/失败回执 | 执行前、执行中、收尾同时发送用例 |
| 上下文正确 | 新要求可在被消费的 Attempt 输入快照中找到，已开始快照不变 | 存储核对和确定性桩测试 |
| 审查闭环不退化 | 仍走 FAIL→修复→PASS；达到上限如实失败 | 现有 verify:scheduler 加场景回归 |
| 流与并发 | 两个 Agent 同时输出时身份正确、不跨任务串流、不重复最终消息 | 乱序事件与交错流测试 |
| 重连与幂等 | 重复 POST 不多执行；快照与增量交错后消息无丢失重复 | 断网、重发、服务重启故障注入 |
| 审批一致 | 聊天与详情是同一 approval；其他房间审批不会冒充当前阻塞 | 两房间并发审批测试 |
| 可用性 | 中文输入法回车不误发；多行、失败重发、阅读时不抢滚动 | 键盘与浏览器手测 |
| 历史兼容 | 旧会话、文件和审查仍可读；流水线行为不被改写 | 迁移前后快照比较 |
| 布局 | 1440/1024/390px 可用，按钮可操作，横向溢出仅限代码/表格 | 浏览器尺寸走查 |
| 阅读效率目标 | 用户在 10 秒内指出“谁在处理、当前问题、下一步”，无需读日志 | 用同一场景对比旧新界面，记录成功率与耗时 |

不以“消息更多”作为成功标准。普通成功工具调用默认折叠；评审失败、审批、执行异常和最终结论必须直接可见。验收同时运行类型检查、前端构建、调度验证和现有 Stub 回归。

## 11. 建议评审结论

建议批准 A＋B，按阶段验收。优先确认四项产品决策：

1. 使用公共团队聊天室，@ 为公开定向交流，第一版不提供私聊。
2. 一个房间包含多轮执行，并共享明确绑定的工作区。
3. 执行中补充采用可追踪的排队消费，第一版不承诺立即打断。
4. 主界面优先展示对话、问题和结果，任务/日志/用量按需展开。

通过以上设计后，用户得到的是有真实协作依据、能继续参与的团队对话体验；技术执行细节仍完整保留，供需要时检查。
