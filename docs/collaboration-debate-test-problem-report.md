## 2. 总体结论

本轮在数据库中完成，但没有按用户语义完成“两个独立辩手各自进行三轮交锋，再由 Reviewer 独立裁决”。实际结果是一份经历多次立场修订、主要由鸡腿统一执笔后两轮、再由参与过编排和修稿的 Reviewer 验收的辩论文档。

问题的共同根因是：Collaboration 已具备自由路由能力，但尚未为多阶段、多角色、有终局约束的协作建立共享状态协议。轮次、角色、立场、完成条件和裁判边界都存在于自然语言中，无法由调度器强制执行。

### AG-COLLAB-01：缺少结构化 Debate Session 与严格轮次状态机（P0）

**现象**：系统只从文本中提取“3 轮”，用于放宽路由深度与 ping-pong 阈值，没有保存当前轮次、阶段、发言者或完成矩阵。三轮限制没有得到协议级执行。

**影响**：系统无法证明双方是否各完成三次发言，也无法阻止跳轮、重复发言或提前评审。

**建议**：引入 Debate Session，至少持久化 `round`、`phase`、`speaker`、双方立场、每轮完成状态和终局状态；只有状态机允许的 Agent 才能创建下一步 Dispatch。

**验收标准**：三轮模式必须形成 6 条独立辩手发言；缺少任意一条时不能进入 Reviewer 阶段；超过三轮的辩手 Dispatch 被拒绝。

### AG-COLLAB-02：多位初始 Agent 并发启动导致多个调度中心（P0）

**现象**：Coder、鸡腿和 Reviewer 同时收到 initial dispatch，随后各自创建交接、并行征询和聚合路线。本轮形成 12 个 Dispatch，出现三个并行调度中心。

**影响**：不同 Agent 各自解释规则，产生互相冲突的轮次安排和角色分工。

**建议**：对带有主持人、裁判或阶段语义的任务建立唯一协调权；Reviewer 注册为保留角色，直到辩手阶段完成才激活。

**验收标准**：开始辩论时只有规定的首位辩手可执行；Reviewer 不产生开场、交接或修稿 Dispatch；调度图中每一轮只有一条合法推进路径。

### AG-COLLAB-03：Agent 角色和立场可被队友自然语言覆盖（P0）

**现象**：Reviewer 最初指定 Coder 支持 Codex、鸡腿支持 Claude Code；Coder 随后发出相反分工，鸡腿接受立场互换，后续又被 Reviewer 改回。

**影响**：用户给出的核心约束被队友消息覆盖，辩论内容和文件头部多次反转。

**建议**：把角色、立场和权限存入不可由普通消息修改的 Run Contract；上下文中明确区分用户约束与 Agent 建议。

**验收标准**：Agent 无法通过 handoff 修改自己或其他 Agent 的正式立场；冲突指令进入可见错误状态；全程显示一致的辩手身份。

### AG-COLLAB-04：三轮真实交锋被降级为单 Agent 代写双方内容（P0）

**现象**：Reviewer 要求鸡腿统一撰写双方第 2 轮反驳和第 3 轮总结。鸡腿明确披露后两轮由其统一执笔。

**影响**：没有形成两个独立 Agent 的真实交锋，最终胜负缺少有效样本。

**建议**：每条正式发言必须由对应辩手的独立 Attempt 产生；禁止其他 Agent 代写并计入该辩手成绩。

**验收标准**：六条辩手发言分别绑定正确 Agent 和轮次；任何代写只能标记为草稿，不能进入正式评审输入。

### AG-COLLAB-05：Reviewer 同时承担主持、修稿和裁判，独立性失效（P0）

**现象**：Reviewer 制定规则、并行征询、纠正立场、要求鸡腿改写双方内容，最后又对自己影响过的内容作出裁决。

**影响**：Reviewer 评审受到自身干预和胜方代写的污染。

**建议**：增加 Reviewer 隔离边界；judging 前只接收评审标准，不得修改辩手内容或创建辩手任务。

**验收标准**：Reviewer 只在全部正式发言冻结后启动；评审输入为只读快照；Trace 中不存在 Reviewer→辩手的内容修订交接。

### AG-COLLAB-06：共享辩论文件存在并发覆盖和版本漂移（P0）

**现象**：多个 Agent 对同一 `debate/codex-vs-claudecode.md` 进行了 6 次写入，文件头部和立场多次变化，没有版本校验或写锁。

**影响**：后写入者可覆盖前序内容，最终文件不能作为可信的原始辩论记录。

**建议**：正式发言使用追加式不可变记录；需要共享文件时增加版本号、compare-and-swap 和冲突提示。

**验收标准**：并发写入不会静默覆盖；每次修改保存作者、基线版本和 diff；Reviewer 从不可变发言记录生成汇总文件。

### AG-COLLAB-07：缺少全局终局屏障，裁定后仍出现迟到发言（P0）

**现象**：Reviewer 在 13:05:27 发布最终裁定，但鸡腿的兄弟 Dispatch 运行至 13:10:10，随后又向用户发布第 2 轮反驳。

**影响**：用户先看到“最终结果”，又看到辩论仍在继续；Run 的语义终态与消息流不一致。

**建议**：Reviewer final action 前等待全部必需 Dispatch；进入 judging 后冻结新辩手路由；裁定发布后取消或丢弃迟到结果。

**验收标准**：最终裁定必须是该 Run 的最后一条业务消息；裁定后不能新增 handoff、辩手结果或工具消息。

### AG-COLLAB-08：执行中断以原始 `terminated` 暴露，聚合继续消费不完整结果（P0）

**现象**：Coder 和鸡腿两个并行 Dispatch 同时以 `terminated` 失败，系统直接把错误发到聊天流；聚合路线随后基于一个成功结果和一个失败占位继续执行。

**影响**：用户无法判断是服务重启、模型失败还是主动取消，Reviewer 使用了不完整输入。

**建议**：区分中断原因并结合 Durable Execution 自动恢复；聚合必须等待恢复完成或显式降级确认。

**验收标准**：可恢复中断不产生原始错误气泡；恢复后替换失败占位；无法恢复时先询问用户，未经确认不得进入评审。

### AG-COLLAB-09：聊天室历史和并发消息污染当前 Dispatch 上下文（P0）

**现象**：`buildContext` 读取整个聊天室最近 19 条消息。Reviewer 引用了上一轮“团队状态检查”中的验收标准提示；并发 Dispatch 的上下文还随执行时间变化。

**影响**：无关历史和兄弟分支进入当前任务，导致角色漂移、错误指令和不可复现行为。

**建议**：上下文以当前 Run 的因果祖先链和已确认公开发言为主；历史消息必须显式引用；Dispatch 创建时冻结上下文版本。

**验收标准**：新 Run 默认不包含上一 Run 的普通消息；同一 Dispatch 重试得到相同上下文；兄弟分支未完成消息不会被提前读取。

### AG-COLLAB-10：缺少分阶段 Token 与调用预算，简单辩论消耗失控（P1）

**现象**：本轮消耗 154,260 Token、31 次 LLM 调用和约 21 分钟；鸡腿单独消耗约 97,763 Token，并有 3 次输出达到 8192 Token 上限。

**影响**：短文本任务需要用户中途扩容，延迟和费用不可预测。

**建议**：为每个角色、轮次和阶段设置调用数与输出 Token 上限；辩论模式默认关闭非必需文件工具。

**验收标准**：三轮辩论在预设总预算内完成；每位辩手每轮最多一次正式生成；超预算前给出可理解的阶段进度和剩余工作。

### AG-COLLAB-11：内部工具、文件和路由消息淹没主聊天流（P1）

**现象**：主聊天显示写入字符数、搜索结果、文件前 499 字、并行聚合、内部 handoff、系统错误和重复文件内容。

**影响**：用户难以识别正式辩论发言，聊天室呈现为调试日志。

**建议**：区分主聊天、协作动态和技术轨迹；默认只在主聊天显示正式发言与裁定。

**验收标准**：工具输出和内部 handoff 默认折叠到轨迹；主聊天清晰呈现六条辩手发言、一条裁定和必要的用户决策。

### AG-COLLAB-12：Reviewer 在没有外部证据时宣称产品事实全部属实（P1）

**现象**：Reviewer 判定价格、基准排名、功能和许可信息“均属实”，但 Trace 只有 `fs.read`、`fs.write` 和 `search.files`，没有外部检索或来源引用。

**影响**：对时效性产品事实作出无法审计的确定性判断，降低裁决可信度。

**建议**：把论证质量和事实核验分开评分；需要事实裁决时强制使用允许的检索工具并附来源。

**验收标准**：未核验的陈述明确标注；“事实属实”必须关联来源或证据 Span；缺少检索能力时 Reviewer 不作确定性事实背书。

## 4. 建议实施顺序

1. 先完成 AG-COLLAB-01、02、03、04、05、07，形成可执行的辩论协议和终局屏障。
2. 再完成 AG-COLLAB-06、08、09，保证记录、恢复和上下文可信。
3. 最后完成 AG-COLLAB-10、11、12，收口成本、交互和评审证据。

## 5. 回归场景

固定使用本报告中的原始用户目标，选择 Coder、鸡腿和 Reviewer。验收时要求系统自动识别两位辩手与终局裁判，按固定立场产生三轮共六条独立发言，冻结后由 Reviewer 基于只读记录裁决。整个 Run 中不得出现立场互换、代写、共享文件覆盖、裁定后迟到消息、无关历史消息或无依据事实背书。
